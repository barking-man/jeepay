# Jeepay 支付结算业务背诵手册

## 使用说明

这份文档以 Jeepay 当前代码和数据库为基础，面向支付、交易、账务、对账、清结算岗位。

背诵顺序：

1. 先背支付主链路和支付状态机；
2. 再背退款、转账、分账和通知；
3. 然后背异常、幂等、并发和补偿；
4. 最后背账务、对账、清分、结算和出款。

全文标记：

- `【Jeepay 现状】`：当前代码真实实现的逻辑；
- `【生产补全】`：Jeepay 未完整实现，但支付结算工程师必须掌握的设计；
- `【背诵结论】`：必须能直接说出的标准答案。

---

# 第一部分：支付结算总框架

## 1. 一条主线

支付中心交易层负责：

> 识别商户和应用，验证请求，选择渠道，创建本地交易记录，调用支付机构，并把同步响应、异步回调和主动查单收敛成最终结果，最后通知商户。

结算系统负责：

> 根据已发生的交易、退款、手续费和分账事实，完成对账、清分、复式记账、结算、出款和差错处理。

【背诵结论】

> 支付解决“用户有没有付成功”，账务解决“债权债务怎么记”，对账解决“两套记录是否一致”，清分解决“各方分多少钱”，结算解决“什么时候结”，出款解决“钱有没有真正打出去”。

## 2. 六个不能混淆的事实

1. 渠道订单创建成功；
2. 用户支付成功；
3. 支付中心本地状态成功；
4. 商户已经收到通知；
5. 账务已经入账；
6. 商户已经结算到账。

六者可能在不同时间完成。

正确关系：

```text
渠道订单创建
    ≠ 用户支付成功
    ≠ 本地支付状态成功
    ≠ 商户通知成功
    ≠ 账务入账
    ≠ 结算出款
```

【背诵结论】

> 渠道订单创建只代表存在可支付的渠道交易；支付成功只代表资金交易事实；通知成功只代表消息送达；账务成功只代表分录已生成；结算成功还要经过出款和银行确认。

## 3. Jeepay 的项目边界

【Jeepay 现状】

- 支持普通商户和服务商模式；
- 支持商户、应用、多商户接入；
- 支持支付方式、渠道路由和费率配置；
- 支持统一下单、查单、关单和过期；
- 支持微信、支付宝、云闪付、PayPal、计全付等渠道适配；
- 支持支付回调、主动查单、补单；
- 支持支付、退款、转账的商户通知；
- 支持退款、转账、分账；
- 支持服务商和商户运营后台。

Jeepay 当前没有完整实现：

- 复式记账；
- 商户资金账户和余额；
- 渠道交易和资金对账；
- 清分；
- 结算批次和结算单；
- 结算出款；
- 银行退票处理；
- 结算后退款追偿；
- 完整风控引擎。

【背诵结论】

> Jeepay 是一套支付交易底座，不等于完整的持牌清结算系统。它提供支付、退款、转账、分账和部分补偿能力，但账务、对账、清分、结算和出款需要二次建设。

# 第二部分：核心名词和业务主体

## 4. 商户、服务商和应用

### 服务商

`isv_no` 标识服务商，是渠道服务商模式下的合作方。

### 商户

`mch_no` 标识商户，是交易收款、退款、分账和对账的业务主体。

商户分两类：

- 普通商户：自己配置渠道商户号和密钥；
- 特约商户：挂在服务商下，需要服务商参数加子商户参数。

### 应用

`app_id` 是实际调用支付 API 的技术主体。

一个商户可以有多个应用，应用持有 `app_secret`，用于请求验签和通知签名。

【背诵结论】

> 服务商是合作主体，商户是业务和资金主体，应用是接口调用和密钥主体。

## 5. 三类订单号

### 商户订单号

例如 `mch_order_no`、`mch_refund_no`。

由商户生成，用于商户业务幂等。

### 平台订单号

例如 `pay_order_id`、`refund_order_id`、`transfer_id`。

由 Jeepay 生成，用于支付中心内部状态和外部渠道调用。

### 渠道订单号

例如 `channel_order_no`。

由微信、支付宝、银联等生成，用于查单、售后、对账和争议处理。

【背诵结论】

> 商户订单号解决业务幂等，平台订单号解决支付中心幂等，渠道订单号解决渠道对账和资金追溯。

## 6. `way_code` 和 `if_code`

`way_code` 表示用户怎样支付：

- `WX_JSAPI`：微信 JSAPI；
- `WX_NATIVE`：微信扫码；
- `WX_BAR`：微信付款码；
- `ALI_APP`：支付宝 App；
- `ALI_WAP`：支付宝 WAP；
- `ALI_BAR`：支付宝付款码；
- `YSF_JSAPI`：云闪付 JSAPI；
- `QR_CASHIER`：Jeepay 聚合收银台；
- `AUTO_BAR`：自动识别付款码类型。

`if_code` 表示调用哪套渠道协议：

- `wxpay`：微信官方接口；
- `alipay`：支付宝官方接口；
- `ysfpay`：云闪付；
- `pppay`：PayPal；
- `plspay`：计全付；
- `xxpay`：小新支付实现。

【背诵结论】

> `way_code` 是支付产品，`if_code` 是渠道接口。用户看到的是支付方式，Jeepay 决定的是渠道协议和结算链路。

## 7. 支付产品、渠道能力、渠道参数和路由

### `t_pay_way`

支付产品字典。

回答：

> 用户能用什么方式支付？

### `t_pay_interface_define`

渠道能力和协议定义。

回答：

> Jeepay 实现了哪个渠道，支持普通商户还是服务商，支持哪些 `way_code`？

### `t_pay_interface_config`

渠道连接参数。

回答：

> 用哪个服务商、商户或应用的密钥、证书和子商户号调用渠道？

多态关系：

```text
info_type=1 → info_id 是服务商号
info_type=2 → info_id 是商户号
info_type=3 → info_id 是应用 ID
```

### `t_mch_pay_passage`

商户应用路由和定价表。

回答：

> 当前商户应用使用某个 `way_code` 时，允许走哪个 `if_code`，商户费率是多少？

关键字段：

```text
mch_no
app_id
if_code
way_code
rate
risk_config
state
```

唯一键：

```text
app_id + if_code + way_code
```

【背诵结论】

> 支付产品决定用户怎么付，渠道定义声明系统能力，渠道参数提供调用凭证，商户应用通道路由决定当前订单最终走哪条渠道以及多少钱费率。

# 第三部分：数据库主模型

## 8. Jeepay 的 23 张表

### 系统与权限

```text
t_sys_user
t_sys_user_auth
t_sys_role
t_sys_user_role_rela
t_sys_entitlement
t_sys_role_ent_rela
t_sys_config
t_sys_log
```

作用：

- 运营平台和商户平台共用一套表结构；
- 通过 `sys_type=MGR/MCH` 隔离；
- 用户关联角色，角色关联菜单和按钮权限；
- 交易结果和人工操作需要审计。

### 商户和渠道配置

```text
t_isv_info
t_mch_info
t_mch_app
t_pay_way
t_pay_interface_define
t_pay_interface_config
t_mch_pay_passage
```

### 交易

```text
t_pay_order
t_refund_order
t_transfer_order
t_mch_notify_record
t_order_snapshot
```

### 分账

```text
t_mch_division_receiver_group
t_mch_division_receiver
t_pay_order_division_record
```

【背诵结论】

> 配置表描述当前策略，交易表保存历史快照；历史订单不能依赖商户当前名称、当前费率或当前密钥重新解释。

## 9. 数据库约束和风险

【Jeepay 现状】

- 数据库没有物理外键；
- 业务关系靠字段和代码维护；
- `t_pay_order` 唯一键为 `mch_no + mch_order_no`；
- 因此同一商户下不同应用也不能复用同一个商户订单号；
- `t_refund_order` 唯一键为 `mch_no + mch_refund_no`；
- `t_transfer_order` 唯一键为 `mch_no + mch_order_no`；
- 通知记录唯一键为 `order_id + order_type`。

当前索引不足的典型位置：

- 退款常用 `pay_order_id + state`，没有联合索引；
- 分账查询常用 `state + created_at` 和 `batch_order_id + state`，没有业务索引；
- 通知巡检缺少 `state + last_notify_time` 索引；
- 管理员按渠道订单号查询支付单时缺少索引。

【背诵结论】

> 唯一键负责防重，业务索引负责性能，物理外键不是支付系统的唯一一致性保障。交易表增大后，状态扫描、退款查询、通知巡检和分账补偿必须按真实 SQL 建索引。

# 第四部分：支付受理完整流程

## 10. 请求进入支付中心

### 第一步：解析请求

商户调用 Jeepay 创建订单，提交：

```text
mchNo
appId
mchOrderNo
wayCode
amount
currency
subject
body
notifyUrl
returnUrl
expiredTime
divisionMode
sign
```

基础校验：

- 必填字段不能为空；
- 金额至少 1 分；
- 金额单位为分；
- `divisionMode` 只能是 0、1、2；
- URL 只允许 HTTP 或 HTTPS。

### 第二步：校验商户和应用

Jeepay 根据 `mchNo + appId` 查询：

- 商户是否存在；
- 商户是否启用；
- 应用是否存在；
- 应用是否启用；
- 应用是否属于该商户。

任一项不满足，直接拒绝。

### 第三步：验签

当前 Jeepay 的逻辑：

1. 把业务对象转成键值集合；
2. 移除 `sign`；
3. 忽略空值；
4. 按字段名排序；
5. 拼接 `key=value&...`；
6. 末尾拼应用密钥；
7. 计算 MD5；
8. 与商户传入的签名比较。

【生产补全】

- 推荐 HMAC-SHA256 或 RSA2；
- 增加 `timestamp` 和 `nonce`；
- 服务端做时间窗校验和重放检测；
- 密钥轮换支持新老版本并行；
- 不记录完整待签名串和敏感字段。

### 第四步：路由

根据：

```text
mch_no + app_id + way_code
```

查询启用中的 `t_mch_pay_passage`。

得到：

```text
if_code
商户费率 rate
risk_config
```

然后校验：

- 渠道定义启用；
- 渠道支持该 `way_code`；
- 普通商户参数已配置；
- 特约商户的子商户参数和服务商参数都已配置；
- 渠道适配器前置检查通过。

### 第五步：生成支付订单

生成：

- 平台支付单号；
- 商户和应用归属；
- `way_code`；
- `if_code`；
- 支付金额；
- 商户费率快照；
- 商户手续费金额；
- 商品信息；
- 通知和跳转地址；
- 分账模式；
- 订单失效时间；
- 初始状态 `INIT`。

### 第六步：先落库，再调渠道

订单以 `INIT` 状态先保存。

原因：

- 固定平台订单号；
- 让渠道请求具备幂等键；
- 外部超时后仍可查单；
- 渠道回调能关联本地订单；
- 后续退款、通知、分账和对账都有主键。

【背诵结论】

> 支付中心验证身份和签名后，按支付产品选出渠道和费率，先生成 `INIT` 本地订单，再调用渠道。数据库和外部渠道无法组成一个事务，因此本地交易凭证必须先持久化。

## 11. 调用渠道后的六类结果

### 明确成功 `CONFIRM_SUCCESS`

渠道已经确认交易成功。

本地处理：

```text
INIT → ING → SUCCESS
```

随后：

- 创建商户通知；
- 判断是否自动分账。

### 明确失败 `CONFIRM_FAIL`

渠道已经明确拒绝或交易失败。

本地处理：

```text
INIT → ING → FAIL
```

不能把明确失败当成未知。

### 处理中 `WAITING`

渠道已经受理，但交易结果尚未完成。

本地处理：

```text
INIT → ING
```

如果渠道同时返回了二维码、`prepay_id`、支付链接或 App 参数，可以返回给商户，让用户继续付款。

如果没有取得有效支付参数，只能返回处理中或结果未知，不能凭空生成新的支付动作。

### 结果未知 `UNKNOWN`

常见原因：

- 网络超时；
- 请求发出但没有收到响应；
- 渠道返回无法确认；
- 签名或数据校验异常。

本地处理：

```text
INIT → ING
```

后续只能按原平台订单号查询，不允许换一个平台订单号重新下单。

### 渠道接口异常 `API_RET_ERROR`

渠道返回异常状态，结果可能未知。

本地进入 `ING`，继续查单。

### 系统异常 `SYS_ERROR`

支付中心自身处理异常。

本地通常保留 `INIT` 或未决状态，需要补偿查询或人工修复。

【背诵结论】

> 明确成功和明确失败才能进入终态；处理中、未知和渠道异常进入 `ING`；支付中心自身异常可能保留 `INIT`。超时不是失败。

## 12. 为什么 `ING` 不等于一定拿到支付参数

`ING` 只表示“交易结果尚未确定”。

### 情况一：渠道订单已创建并返回支付参数

例如微信 Native 已经返回 `code_url`。

此时可以：

- 返回二维码；
- 用户扫码付款；
- Jeepay 后台等待回调或查单。

### 情况二：调用超时或响应丢失

此时可能：

- 渠道订单没有创建；
- 渠道订单已经创建，但 Jeepay 没拿到参数。

不能：

- 凭空生成支付参数；
- 盲目换单号重下；
- 直接告诉用户支付失败。

只能后台查原渠道。

【背诵结论】

> 是否返回支付参数取决于渠道是否真的创建订单并返回可用参数；`ING` 只决定后台必须继续收敛，不决定前端是否可以发起支付。

## 13. 支付订单主状态机

| 状态码 | 状态 | 含义 |
|---:|---|---|
| 0 | `INIT` | 本地订单已创建，尚无最终结果 |
| 1 | `ING` | 支付中或结果未知 |
| 2 | `SUCCESS` | 支付成功 |
| 3 | `FAIL` | 支付失败 |
| 4 | `CANCEL` | 已撤销，当前代码未实际写入 |
| 5 | `REFUND` | 已累计全额退款 |
| 6 | `CLOSED` | 未支付订单关闭或过期 |

完整迁移：

```text
INIT → ING
INIT → SUCCESS
INIT → FAIL
INIT → CLOSED
ING  → SUCCESS
ING  → FAIL
ING  → CLOSED
SUCCESS → SUCCESS      部分退款
SUCCESS → REFUND       累计全额退款
```

【Jeepay 现状】

- 条件更新要求旧状态符合预期；
- 同步成功通常先 `INIT → ING`，再 `ING → SUCCESS`；
- 支付过期任务会把 `INIT/ING` 直接改 `CLOSED`；
- 支付回调主体只明确处理 `ING`；
- `CANCEL=4` 未实际使用。

【背诵结论】

> 支付状态是条件迁移，不是按消息到达顺序覆盖。`ING` 是等待最终结果，不是支付成功，也不是支付失败。

## 14. 支付订单的附加状态

### `refund_state`

```text
0 未发生实际退款
1 部分退款
2 全额退款
```

### `division_mode`

```text
0 不允许分账
1 支付成功后自动分账
2 商户手动分账
```

### `division_state`

```text
0 未发生分账
1 等待分账任务
2 分账处理中
3 本轮分账任务结束
```

### `notify_state`

```text
0 未开始通知
1 已经开始通知
```

【背诵结论】

> `state` 表示支付结果，`refund_state` 表示退款汇总，`division_state` 表示分账任务，`notify_state` 表示通知是否开始。四个字段互不替代。

# 第五部分：渠道回调、查单和通知

## 15. 渠道异步回调

### 标准步骤

1. 从回调地址或报文识别渠道和订单号；
2. 查询本地支付单；
3. 加载商户和渠道配置；
4. 验证渠道签名；
5. 校验渠道商户号和应用号；
6. 校验订单号、金额和币种；
7. 检查本地状态；
8. 满足条件时执行状态 CAS；
9. 成功时触发商户通知和自动分账；
10. 按渠道协议返回 ACK。

### 验签成功不代表业务匹配

还必须验证：

- 回调订单是否属于该本地订单；
- 回调中的渠道商户是否匹配；
- 金额和币种是否一致；
- 渠道状态是否可信；
- 回调 URL 中的订单号和报文订单号是否一致。

【背诵结论】

> 回调必须“验签通过、业务字段匹配、本地状态允许”三个条件同时满足，才能改变订单。

## 16. 六类回调场景

### 正常成功

```text
ING + 渠道成功 → SUCCESS
```

### 正常失败

```text
ING + 渠道失败 → FAIL
```

### 重复成功

本地已经是 `SUCCESS`：

- 不重复迁移；
- 不重复分账；
- 不重复创建通知；
- 按渠道要求返回 ACK。

### 乱序回调

先失败后成功：

- 不按到达顺序覆盖；
- 主动查渠道；
- 以最终可信状态为准。

### 早到回调

回调早于同步响应后的本地更新：

- 不能直接丢弃；
- 保存回调证据；
- 重新查询或延迟处理；
- 防止本地已经成功但状态仍停在 `INIT/ING`。

### 晚到成功

本地可能已经 `CLOSED`。

这属于高风险差错：

- 查渠道；
- 判断是否已履约；
- 未履约可补单；
- 不应履约可退款；
- 进入差错和日终对账。

## 17. 商户查询和渠道查询不是一件事

### 商户查询

商户调用 Jeepay 的查询接口，读取 Jeepay 本地支付、退款或转账订单。

特点：

- 本地查询；
- 返回 Jeepay 当前状态；
- 不必然实时调用渠道。

### 渠道查询

Jeepay 内部补单任务调用微信、支付宝等查询接口。

目的：

- 弥补回调丢失；
- 解决请求超时；
- 解决本地状态未更新；
- 确认最终交易结果。

【背诵结论】

> 商户查询看 Jeepay 当前记录，渠道查询获取外部真实结果；两者不是同一个接口层次。

## 18. 主动查单机制

【Jeepay 现状】

### 延迟 MQ 查单

- 渠道适配器把响应标记为“需要查询”时才发送；
- 首次延迟 5 秒；
- 只有订单仍为 `ING` 才查询；
- 查询返回空、无状态或 `WAITING` 时继续延迟查询；
- 查询返回 `UNKNOWN` 时，当前 MQ 接收器不会再发下一条消息，后续主要依赖分钟级定时扫描；
- 单条 MQ 链最多查询 6 次。

### 定时补单

- 每分钟运行；
- 扫描创建超过 10 分钟的 `ING` 支付单；
- 每页处理 100 条；
- 查询渠道；
- 成功或失败则更新；
- 未知则下轮继续。
- 当前使用页码分页；处理过程中列表数量变化时，存在跳过部分记录的边界风险。

### 作用

- 回调丢失兜底；
- 请求超时兜底；
- 回调乱序兜底；
- 本地事务失败后恢复交易事实。

### 当前风险

- MQ 消息丢失后短期链中断；
- 定时任务多实例时可能重复扫描；
- `INIT` 订单不在常规补单条件内；
- 没有持久化查询次数和下一次查询时间；
- 长时间 `ING` 没有强制人工升级。

【背诵结论】

> 渠道适配器标记需要查询时，延迟 MQ 负责短周期快速收敛；所有超过 10 分钟仍为 `ING` 的支付单由定时扫描兜底。两者都必须按原平台订单号查询，不能换单重下。

## 19. 商户异步通知

### 创建时机

支付成功时创建支付通知。

退款和转账在明确成功或失败时创建通知。

当前支付失败路径没有直接创建支付失败通知，商户应依赖同步响应或主动查询。

### 唯一性

```text
order_id + order_type
```

`order_type`：

```text
1 支付
2 退款
3 转账
```

### 通知内容

- 商户号；
- 应用 ID；
- 商户订单号；
- 平台订单号；
- 渠道订单号；
- 金额；
- 币种；
- 状态；
- 请求时间；
- 签名。

### 通知状态

```text
1 通知中
2 通知成功
3 通知失败
```

### 重试

默认最多 6 次：

```text
第1次立即
第2次延迟30秒
第3次延迟60秒
第4次延迟90秒
第5次延迟120秒
第6次延迟150秒
```

商户必须返回纯 `SUCCESS`。

当前 HTTP 超时为 20 秒。

### 人工重发

失败通知可以由运营人员重新置为通知中，并增加通知次数上限后重新投递。

### 重要边界

- 通知失败不能回滚支付；
- HTTP 200 不等于商户业务成功；
- 通知是至少一次投递；
- 商户必须按平台订单号幂等；
- 同一通知必须复用同一业务记录。

【背诵结论】

> 支付成功是资金交易事实，通知成功是消息送达事实。通知失败后继续重试或人工补发，不能修改支付结果。

# 第六部分：关单、过期和支付异常

## 20. 商户主动关单

只允许关闭 `INIT` 和 `ING`。

### `INIT` 关单

尚未形成确定渠道交易，可直接：

```text
INIT → CLOSED
```

### `ING` 关单

必须调用渠道关单：

```text
渠道明确关闭成功
→ ING → CLOSED
```

渠道关闭失败或未知时：

- 本地不能盲目关闭；
- 主动查询渠道；
- 继续等待最终结果。

## 21. 支付过期

支付单默认两小时过期。

【Jeepay 现状】

- 每分钟执行过期任务；
- 将已过失效时间且仍为 `INIT/ING` 的订单直接改 `CLOSED`。

风险：

- 没有先调用渠道关单；
- 用户可能已经支付；
- 本地关闭后晚到成功回调无法正常改变状态。

【生产补全】

- 过期前尝试渠道关单；
- 关单后查询确认；（调了关单接口，还要再主动查询一次，确认是否真的关闭）
- 对晚到成功进入差错；（渠道认为关闭成功，但支付机构推送了支付成功的结果）
- - 查询渠道确认确实成功；
    保存渠道订单号和回调证据；
    判断商户是否已经履约；
    未履约可以考虑补单；如果关单后又收到支付机构的回调说订单支付成功，那这时候要调商户接口判断商户是否履约，如果已经履约则补单（改状态为支付机构返回结果），如果没有履约，则取决于业务允许继续履约：补单并通知商户发货； 不允许继续履约：原路退款；库存已经没有了：退款并通知用户。
    不应继续履约则原路退款；
    补做或修正账务；
    通知商户和客服处理。****
- 日终对账发现“本地关闭、渠道成功”。

## 22. 关单、撤销、退款的区别

```text
关单：用户还没支付成功，阻止继续付款
撤销：撤销授权或尚未清算交易，具体看渠道
退款：支付成功后，把资金原路退回
```

【Jeepay 现状】

- 有关单；
- 主状态定义了 `CANCEL=4`，但没有实际写入；
- 退款完整存在。

【背诵结论】

> 关单不退款，撤销不等于退款，退款必须基于成功支付订单。

## 22.1 Jeepay 当前是否存在撤销逻辑

【Jeepay 现状】

- `PayOrder` 定义了 `STATE_CANCEL=4`；
- 全部业务代码中没有把它写入支付订单；
- 没有 `/api/pay/cancel` 之类的商户撤销接口；
- 没有统一的渠道撤销能力接口；
- 支付补单 MQ 达到查询上限后，只留下“调用撤销订单接口”的 TODO；
- 微信查询和回调可能返回渠道状态 `REVOKED`；
- 当前微信适配器把 `REVOKED` 和 `CLOSED`、`PAYERROR` 一起映射为明确失败；
- 因此渠道已撤销通常会让本地进入 `FAIL`，而不是 `CANCEL`。

准确结论：

> Jeepay 有“已撤销”状态常量和渠道状态识别，但没有形成独立的本地撤销订单、撤销接口、渠道撤销调用和撤销补偿闭环。当前真正可用的是关单和退款。

## 22.2 关单、撤销、退款的区别

### 关单

目标是阻止未支付订单继续付款。

```text
INIT → CLOSED
ING  → 调渠道关单 → CLOSED
```

关单通常不产生资金退回。

### 撤销
触发场景：调了支付机构接口以后，如果超时未收到响应，支付结果不明确，比如支付系统超时/网络异常、支付接口返回失败，但不确定资金是否实际划扣
撤销的语义取决于渠道和产品，可能包括：

- 撤销尚未付款的授权；
- 撤销未清算交易；
- 对已受理但未完成的交易执行反向操作；
- 银行卡授权场景下的 void；
- 某些渠道把取消付款称为 revoke。

撤销可能导致资金恢复，但是否等同于退款取决于交易阶段。
未扣款时撤销只是释放授权（此时钱还在用户账户，只是被银行冻结了一部分，防止用户使用，释放授权就是解冻资金）；
已扣款未清算时可以冲正（用户账户的钱被划走，但还未进入商户的账户，即还未清算，冲正就是在这个阶段进行，撤销交易，让资金回流，清算通常要次日进行）
已清算或不支持撤销时才走退款。
用户侧可能都看到“钱退回来了”，系统内部必须区分授权释放、撤销、冲正和退款。，未扣款只是释放授权，怎么理解
预授权交易：
授权-请款-结算
- 请款：是预授权交易里的第二步，核心逻辑是：把之前“冻结”在用户账户里的钱，确定归属于商户（但最后到达商户账户，需要走结算流程），通常银行要求7天内必须请款，否则会将钱原路退回到用户。
- 自动请款：授权和请款几乎同时完成。用户付款时，银行冻结资金后立刻划走（钱进入支付机构的账户，支付机构会把钱记账到一个虚拟商户号（此时商户拥有钱但用不了），之后等待银行结算之后，钱才进入商户银行卡），这是大多数普通支付（如扫码买瓶水）的默认逻辑。 
- 手动请款：先授权冻结，商户在完成服务或发货后，再单独发起请款。典型场景是酒店押金（先冻结一笔钱，退房时按实际消费请款）或租车。
- 预授权交易中的余额冻结是银行或者支付机构干的（具体取决于钱存在哪里）
- 清算：发生在结算之前，核心是“算账”。它负责在金融机构（如发卡行、收单行、支付机构）之间传递支付指令、进行清分和轧差，算出谁最终该收多少钱、谁该付多少钱。它本身不转移实际资金，只是为后续的资金划转做好准备。
- 结算：发生在清算之后，核心是“给钱”。它根据清算算出来的结果，完成资金从付款方到收款方的最终、实际转移，把债权债务彻底了结
### 退款

退款针对已经成功的支付交易，将全部或部分资金原路退回。

【背诵结论】

> 关单是阻止付款，撤销是取消授权或未完成交易，退款是退回已支付资金。

## 22.3 生产系统应如何设计撤销

【生产补全】

撤销必须有独立业务对象或明确的撤销记录，例如：

```text
cancel_id
pay_order_id
channel_order_no
cancel_type
amount
state
channel_code
channel_message
requested_at
completed_at
operator
reason
```

推荐状态：

```text
INIT
→ PROCESSING
→ SUCCESS
→ FAIL
→ UNKNOWN
```

处理流程：

1. 校验原支付单和商户身份；
2. 判断渠道、支付产品和当前交易阶段是否支持撤销；
3. 按原渠道订单号发起撤销；（支付机构的撤销接口返回close：则表示未扣款、此时支付中心直接更新状态为已关闭即可，如果是refund，说明渠道进行了退款（可能是退款也可能是冲正），所以支付中心要按照退款的性质记录流水（记录在退款表））
4. 明确成功则记录撤销成功；
5. 明确失败则记录失败；
6. 结果未知则保持处理中并主动查询；
7. 根据撤销前是否已经扣款、冻结或记账，决定是否生成冲正或释放分录；
8. 如果交易已经清算或渠道不支持撤销，转退款；
9. 撤销和退款必须在业务状态上串行互斥，防止并发执行；撤销明确失败后才允许转退款。

## 22.3.1 撤销成功是否一定需要账务冲正

不一定。

### 尚未扣款，只释放授权冻结

此时没有实际资金支付，也没有支付收入或渠道应收。

处理原则：

- 记录撤销成功；
- 释放授权冻结或额度占用；
- 不生成支付冲正分录；
- 不创建退款单；
- 不需要冲减手续费收入。

如果账务系统单独记录授权冻结，可以做“释放冻结”的辅助记录，但这不是资金退款冲正。

### 已经授权或占用额度，但尚未扣款

处理原则：

- 释放授权占用；
- 不确认手续费收入；
- 不确认商户应付；
- 根据账务模型决定是否记录授权释放事件。

### 已扣款但尚未清算

如果系统已经确认支付成功并生成：

- 渠道清算应收；
- 商户应付；
- 手续费收入；

那么撤销成功后必须冲正这些已经产生的分录。

### 已经清算或结算

通常不能再撤销，应转退款，并按照退款影响：

- 渠道应收；
- 商户余额或欠款；
- 退款负债；
- 手续费返还规则；
- 银行资金；

分别记账。

【背诵结论】

> 只有撤销前已经形成资金扣款或账务事实，才需要按原分录冲正。未扣款、仅释放授权冻结的场景不需要支付退款冲正，只记录撤销成功并释放冻结；撤销与退款串行互斥，撤销明确失败后才能转退款。

## 22.4 状态如何设计

Jeepay 当前只有一个 `CANCEL=4`，不足以表达撤销过程。

生产系统建议区分：

```text
支付订单状态：
INIT / ING / SUCCESS / FAIL / REFUND / CLOSED

撤销订单状态：
INIT / PROCESSING / SUCCESS / FAIL / UNKNOWN
```

不要长期用多个并发字段表达同一事实。

推荐保留：

- 支付单 `state`；
- 撤销单 `state`；
- 退款单 `state`；
- 三者之间通过原支付单号关联。

## 22.5 撤销与晚到支付

如果已经发起撤销，但渠道之后又回调支付成功：

1. 不能直接忽略；
2. 按渠道订单号查询最终状态；
3. 判断撤销和支付成功是否存在时序冲突；
4. 明确已支付且撤销失败时，进入退款流程；
5. 保存撤销请求、渠道结果和支付回调证据；
6. 日终通过渠道账单核对。

## 22.6 当前 Jeepay 的准确表述

面试或沟通时应说：

> Jeepay 当前完整实现的是未支付订单关单和已支付订单退款。代码中定义了 `CANCEL=4`，也能识别部分渠道的 `REVOKED` 状态，但没有真正的商户撤销接口和统一渠道撤销链路，达到支付查单上限时调用撤销仍是 TODO。因此不能把 Jeepay 描述成已经完整支持撤销。

【背诵结论】

> Jeepay 当前有撤销状态定义和渠道 `REVOKED` 识别，但没有完整撤销实现；生产系统应建立独立撤销单、渠道撤销接口、异步查询、幂等控制和账务冲正，并在渠道不支持撤销或已清算时转为退款。

# 第七部分：退款

## 23. 退款业务定义

退款是将已成功支付的钱全部或部分退回原付款方。

退款必须：

- 关联原支付单；
- 使用原支付渠道；
- 有独立退款单；
- 有独立退款状态；
- 受累计金额限制；
- 可查询；
- 可通知；
- 可审计。

## 24. 退款前置检查

【Jeepay 现状】

1. 商户和应用验签；
2. 原支付单存在；
3. 原支付状态是 `SUCCESS`；
4. 尚未全额退款；
5. 本次退款不超过剩余可退余额；
6. 同一支付单不能已有 `ING` 退款；
7. 成功退款总额加本次金额不超过支付金额；
8. 商户退款单号不重复；
9. 原渠道支持退款；
10. 渠道参数有效。

## 25. 退款状态

| 状态码 | 状态 | 含义 |
|---:|---|---|
| 0 | `INIT` | 退款单已创建 |
| 1 | `ING` | 退款中或未知 |
| 2 | `SUCCESS` | 退款成功 |
| 3 | `FAIL` | 退款失败 |
| 4 | `CLOSED` | 退款任务关闭或过期 |

迁移：

```text
INIT → ING
INIT → SUCCESS
INIT → FAIL
ING  → SUCCESS
ING  → FAIL
INIT/ING → CLOSED
```

## 26. 退款成功如何更新支付单

退款成功时，同一事务中：

1. 退款单 `ING → SUCCESS`；
2. 支付单 `refund_times + 1`；
3. 支付单 `refund_amount + 本次退款金额`；
4. 计算累计退款状态；
5. 部分退款：

```text
refund_state = 1
支付主状态仍为 SUCCESS
```

6. 全额退款：

```text
refund_state = 2
支付主状态 SUCCESS → REFUND
```

SQL 更新支付单时还会检查：

```text
当前支付状态必须是 SUCCESS
已退金额 + 本次退款金额 <= 支付金额
当前退款状态必须是未退款或部分退款
```

## 27. 退款回调、查单和补偿

退款进入 `ING` 后：

- 渠道退款回调可以更新结果；
- 定时补单每分钟扫描退款中订单；
- 调原渠道查询退款状态；
- 明确成功或失败后通知商户。

【Jeepay 现状】

- 退款补单没有显式次数上限；
- 退款单默认两小时过期；
- 过期任务会把 `INIT/ING` 直接改为 `CLOSED`。

## 28. 退款最重要的异常

### 退款请求超时

不能再次退款。

处理：

```text
保持 ING
→ 按退款单号查询原渠道
→ 成功则补本地状态
→ 失败才允许后续处理
```

### 退款成功但本地失败

渠道退款已发生，本地事务失败。

处理：

- 查询渠道；
- 修复退款单；
- 回写支付单累计退款；
- 补记退款账务；
- 幂等补发通知。

### 本地退款关闭但渠道后成功

高风险差错：

- 资金已经退回用户；
- 本地累计退款金额没有增加；
- 支付单可能仍显示部分可退。

处理：

- 以渠道回单和退款账单为准；
- 人工恢复退款事实；
- 调整账务；
- 防止再次超退。

### 并发退款

Jeepay 查询是否存在 `ING` 退款，本质上仍是先查后改。

生产必须通过：

- 支付单锁；
- 退款额度冻结；
- 唯一占用；
- 原子金额更新。

## 29. 结算后退款

如果钱已经结算给商户，再退款时：

```text
平台可先向用户退款
→ 从商户可结算余额扣回
→ 余额不足形成商户欠款
→ 冻结后续结算或下期抵扣
```

【背诵结论】

> 退款必须独立、原路、可查询；退款成功才累计已退金额；退款超时只是未知，不能重复退款；结算后退款必须有追偿和负余额机制。

# 第八部分：转账和代付

## 30. 转账业务定义

转账是 Jeepay 主动向指定账户付款。

常见入账方式：

```text
WX_CASH      微信零钱
ALIPAY_CASH  支付宝
BANK_CARD    银行卡
```

它不关联原支付单，是独立出款交易。

## 31. Jeepay 转账流程

1. 商户提交带签名请求；
2. 校验商户和应用；
3. 校验商户订单号唯一；
4. 校验通知地址；
5. 商户明确指定 `if_code`；
6. 校验渠道已开通；
7. 校验渠道支持收款方式；
8. 创建转账单 `INIT`；
9. 渠道前置检查；
10. 发起转账；
11. 根据渠道结果进入终态或 `ING`；
12. 回调或查询继续收敛；
13. 成功或失败通知商户。

## 32. 转账状态

| 状态码 | 状态 | 含义 |
|---:|---|---|
| 0 | `INIT` | 转账单已创建 |
| 1 | `ING` | 转账中或未知 |
| 2 | `SUCCESS` | 转账成功 |
| 3 | `FAIL` | 转账失败 |
| 4 | `CLOSED` | 已定义，当前未实际写入 |

## 33. 转账查询

每分钟扫描处于 `ING` 且创建时间在最近一天内的转账单：

- 明确成功：`ING → SUCCESS`；
- 明确失败：`ING → FAIL`；
- 未知：保持 `ING`。

Jeepay 没有转账过期任务，也没有类似支付的 6 次 MQ 查询链。超过一天仍为 `ING` 的转账单不会再被该定时任务自动扫描，必须依赖告警和人工处理。

## 34. 转账线上风险

### 超时

渠道可能已经出款，只是响应丢失。

必须：

```text
保持 ING
→ 查询原转账单
→ 确认成功或失败
```

禁止：

```text
超时
→ 判失败
→ 新单号重新出款
```

否则可能重复出款。

## 35. Jeepay 转账的业务缺口

【生产补全】

- 商户余额校验；
- 提现密码或二次验证；
- 资金冻结；
- 提现手续费；
- 出款审批；
- 批量代付；
- 银行退票；
- 出款账务；
- 结算与代付区分。

【背诵结论】

> Jeepay 的转账单是单笔渠道出款交易，不等于完整结算。超时后先查原单，绝不能换单号重复出款。

# 第九部分：分账

## 36. 分账业务定义

分账是把一笔交易收入按规则分配给多个接收方。

分账不等于结算。

## 37. 分账数据

### 接收方组

`t_mch_division_receiver_group`

自动分账组由 `auto_division_flag` 标识。

### 接收方

`t_mch_division_receiver`

关键维度：

```text
mch_no
app_id
if_code
receiver_group_id
acc_type
acc_no
relation_type
division_profit
state
```

### 分账记录

`t_pay_order_division_record`

每条记录对应一个支付单对一个接收方的分账。

## 38. 自动分账流程

1. 下单时 `division_mode=1`；
2. 支付成功；
3. 支付单分账状态 `0 → 1`；
4. 延迟 80 秒发送分账 MQ；
5. 消费者开始任务，`1 → 2`；
6. 查询自动分账组；
7. 计算接收方比例和金额；
8. 保存分账记录；
9. 调渠道分账；
10. 更新单条记录；
11. 父状态 `2 → 3`。

## 39. 手动分账

前置：

```text
支付状态 SUCCESS
division_mode=2
division_state=0
接收方或组有效
```

## 40. 可分配金额

```text
可分配金额
= 支付金额
- 商户手续费
- 已成功退款金额
- 已成功分账金额
```

小于等于 0 时取 0。

## 41. 分账状态

父订单：

```text
0 未发生分账
1 等待分账任务
2 分账处理中
3 本轮分账任务结束
```

单条记录：

```text
0 WAIT    待分账
1 SUCCESS 明确成功
2 FAIL    明确失败
3 ACCEPT  上游已受理
```

【背诵结论】

> 父订单状态 3 只表示本轮任务结束，不代表每个接收方成功。最终结果必须看每条分账记录。

## 42. 分账异常和补偿

### 上游受理

记录为 `3 ACCEPT`。

超过约 5 分钟后，定时任务查询渠道：

```text
明确成功 → SUCCESS
明确失败 → FAIL
未知 → 继续等待
```

### 明确失败

运营或商户可以重发。

重发：

- 父订单 `3 → 1`；
- 失败记录 `2 → 0`；
- 生成新批次号；
- 重新调用渠道。

### 部分成功

一个支付单的多条分账记录可能：

- 部分成功；
- 部分失败；
- 部分仍已受理。

不能只看父状态。

### 分账后退款

需要解决：

- 已分给接收方的钱如何退回；
- 平台是否垫付；
- 是否形成负余额；
- 是否下期扣回；
- 渠道是否支持已分账交易退款。

【背诵结论】

> 分账决定收入分配，结算决定出款。分账成功不代表结算完成，分账后退款必须明确资金追偿责任。

# 第十部分：其他支付相关功能

## 43. 聚合收银台 `QR_CASHIER`

聚合收银台和普通直接下单不同。

流程：

1. 商户传入 `QR_CASHIER`；
2. Jeepay 先生成一笔 `INIT` 支付单；
3. 返回 Jeepay 收银台跳转地址或二维码地址；
4. 用户在收银台选择微信、支付宝等实际支付方式；
5. 用户选定后再次执行实际支付方式下单；
6. 原支付单更新真实 `way_code`、`if_code` 和费率；
7. 调用具体渠道；
8. 返回支付参数或结果。

【背诵结论】

> 聚合收银台不是直接调用单一渠道，而是先创建统一支付单，再让用户选择实际支付方式，最终仍走普通渠道下单和结果收敛。

## 44. 付款码支付 `AUTO_BAR`

付款码是一串数字，需要先识别支付机构。

当前规则：

- 18 位、以 10～15 开头：微信；
- 16～24 位、以 25～30 开头：支付宝；
- 19 位、以 62 开头：云闪付。

识别后转换成具体：

```text
WX_BAR
ALI_BAR
YSF_BAR
```

再进入正常路由。

【背诵结论】

> 聚合付款码只是支付方式识别层，识别后仍要按商户应用的通道路由选择渠道。

## 45. 渠道用户标识获取

某些支付方式需要：

- 微信 `openid`；
- 支付宝 `user_id`；
- 小程序用户标识。

Jeepay 支持通过渠道 OAuth 或跳转流程获取用户标识，然后把 `channelUserId` 带入下单。

用途：

- JSAPI；
- 小程序支付；
- 转账到零钱；
- 渠道侧用户匹配。

风险：

- 用户标识必须与商户配置匹配；
- 不能使用另一个应用的 openid；
- OAuth state 必须防篡改和重放；
- 用户拒绝授权要有明确返回流程。

## 46. 支付页面同步跳转

`returnUrl` 用于用户付款后浏览器返回商户页面。

同步跳转只用于用户体验。

不能只凭同步跳转页面判断支付成功。

真正可信依据：

- 渠道异步回调；
- Jeepay 主动查询；
- 渠道账单对账。

【背诵结论】

> 页面跳转不是支付事实，服务端异步通知和主动查询才是。

# 第十一部分：完整支付链路背诵版

## 47. 正常支付全过程

按下面顺序完整背诵：

1. 用户在商户 App、网页或小程序选择商品；
2. 商户业务系统创建业务订单；
3. 商户服务端使用 `mchNo`、`appId`、`mchOrderNo`、`wayCode`、金额等字段调用 Jeepay；
4. Jeepay 校验字段、商户、应用和签名；
5. Jeepay 按 `mchNo + appId + wayCode` 查商户通道路由；
6. 路由给出 `ifCode` 和商户费率；
7. Jeepay 校验渠道定义、渠道参数和前置条件；
8. Jeepay 生成平台订单号；
9. Jeepay 保存金额、费率、手续费、通知地址和分账模式；
10. 支付单以 `INIT` 落库；
11. Jeepay 调用微信、支付宝等创建渠道交易；
12. 渠道明确成功则收敛成功；明确失败则收敛失败；未知则进入 `ING`；
13. 如果可以拿到二维码、prepay_id 或 App 参数，Jeepay 返回商户；
14. 商户前端拉起微信、支付宝或展示二维码；
15. 用户确认支付；
16. 渠道异步回调 Jeepay；
17. 回调签名和金额等校验通过后，Jeepay 把 `ING` 条件更新为 `SUCCESS/FAIL`；
18. 如果回调缺失，Jeepay 按原平台订单号主动查询；
19. 支付成功后创建商户通知记录；
20. Jeepay 异步通知商户，失败后重试；
21. 商户返回约定的 `SUCCESS`；
22. 商户进行业务履约；
23. 如果启用自动分账，支付成功后延迟 80 秒发起分账；
24. 日终用渠道账单、本地交易和账务进行对账；
25. 对账确认后清分和记账；
26. 满足账期后生成结算单和出款单；
27. 出款渠道返回成功；
28. 银行或渠道回单确认到账；
29. 如发生退款、拒付或差错，反向记账并调整下一期结算。

## 48. 支付成功后的四个动作

```text
1. 本地支付状态变 SUCCESS
2. 创建商户通知记录
3. 判断自动分账
4. 产生账务事件
```

当前 Jeepay 已实现前三项。

第四项是生产补全。

【背诵结论】

> Jeepay 成功回调后先完成支付状态迁移，再执行通知和自动分账；生产账务系统还应在交易事实确认后生成唯一账务事件。

## 49. 一张图不用看时的口述

> 用户先和商户业务系统交互，商户服务端同步调用 Jeepay，Jeepay 验签和选路后创建 `INIT` 支付单，再同步调用渠道创建交易。用户通过渠道完成付款，渠道异步回调支付结果；如果回调缺失，Jeepay 按原平台订单号主动查询。Jeepay 把 `ING` 收敛为终态后通知商户，成功且启用自动分账时再发分账任务。支付发生后的渠道账单和本地交易进入对账、清分、记账和结算，最终出款并由银行回单确认。

# 第十二部分：状态组合和业务判断

## 50. 典型场景状态表

| 场景 | 支付状态 | 退款汇总 | 分账状态 | 其他事实 |
|---|---|---|---|---|
| 刚创建订单 | `INIT` | 0 | 0 | 无渠道结果 |
| 等待付款 | `ING` | 0 | 0 | 可能已有支付参数 |
| 请求超时 | `ING` | 0 | 0 | 渠道订单是否存在未知 |
| 明确支付失败 | `FAIL` | 0 | 0 | 无退款 |
| 未支付过期 | `CLOSED` | 0 | 0 | 渠道可能仍可支付，需要确认 |
| 支付成功 | `SUCCESS` | 0 | 0 或等待分账 | 通知可能未送达 |
| 通知失败 | 支付状态不变 | 不变 | 不变 | 通知记录为通知中或失败 |
| 一笔退款中 | `SUCCESS` | 原值 | 原值 | 退款单为 `ING` |
| 部分退款成功 | `SUCCESS` | 1 | 原值 | 累计退款小于支付金额 |
| 全额退款成功 | `REFUND` | 2 | 原值 | 累计退款等于支付金额 |
| 自动分账处理中 | `SUCCESS` | 0 | 2 | 分账记录正在处理 |
| 分账本轮结束 | `SUCCESS` | 0 | 3 | 记录可能混合成功、失败、已受理 |
| 转账成功 | 不涉及支付状态 | 不涉及 | 不涉及 | 转账单为 `SUCCESS` |

## 51. 状态判断五步法

遇到任何支付问题，按顺序问：

1. 交易对象是支付、退款、转账还是分账？
2. 当前对象的状态字段是什么？
3. 渠道是否明确成功、明确失败或未知？
4. 本地状态迁移是否满足前置状态？
5. 后续副作用是否已经完成：通知、账务、分账、结算？

# 第十三部分：异常处理和线上兜底

## 52. 异常处理总原则

```text
先保护资金
再确认渠道事实
再做幂等修复
再做账务调整
最后复盘规则和监控
```

禁止：

- 直接改数据库让订单成功；
- 超时直接判失败；
- 换订单号重新下单；
- 重复退款；
- 重复出款；
- 对账差异直接覆盖；
- 删除历史分录；
- 把 MQ 成功当成业务成功。

## 53. 支付请求超时

现象：

- 商户没拿到响应；
- Jeepay 订单为 `INIT/ING`；
- 渠道可能已经创建交易。

处理：

1. 用商户订单号查询 Jeepay；
2. 用平台订单号查询渠道；
3. 确认渠道是否创建；
4. 有支付参数且未付款，可以继续支付；
5. 渠道成功则补本地状态；
6. 渠道明确失败才结束；
7. 未知则继续补偿。

不能：

```text
超时 → 新订单号 → 再下单
```

## 54. 渠道成功但 Jeepay 仍为 `ING`

排查：

- 回调是否到达；
- 回调验签是否通过；
- 回调业务字段是否匹配；
- 本地 CAS 是否失败；
- 补单任务是否运行；
- MQ 是否积压；
- 查询渠道是否成功。

兜底：

- 主动查渠道；
- 明确成功后按条件更新；
- 执行通知；
- 检查自动分账；
- 补记账务事件。

## 55. 渠道成功但本地没有订单

高风险无主交易。

处理：

1. 查询商户号、平台订单号和渠道订单号；
2. 核对原始商户请求；
3. 判断是否回调伪造；
4. 判断是否本地数据被误删或路由错误；
5. 确认渠道真实扣款后进入人工差错；
6. 根据业务是否履约选择补单或退款；
7. 日终再次对账。

绝不能直接创建一笔“看起来像正常”的订单掩盖数据缺失。

## 56. Jeepay 已关闭但渠道成功

处理：

1. 保留本地关闭记录；
2. 确认渠道成功；
3. 判断用户是否已经得到服务；
4. 未履约可以补单或退款；
5. 不应重复履约则退款；
6. 生成差错单；
7. 修正账务。

## 57. 支付成功但商户未收到通知

检查：

- 通知记录是否存在；
- `notify_count`；
- `notify_count_limit`；
- `res_result`；
- `last_notify_time`；
- 商户地址和证书；
- MQ 和线程池；
- 商户返回是否为纯 `SUCCESS`。

处理：

- 保持支付成功；
- 继续重试；
- 超过阈值人工重发；
- 提供商户主动查单；
- 检查是否重复通知。

## 58. 重复回调

幂等防线：

```text
支付状态 CAS
通知记录唯一键
分账父状态条件更新
分账记录状态条件更新
账务事件唯一键
```

只要本地已经成功：

- 不重复改支付状态；
- 不重复创建通知；
- 不重复分账；
- 返回渠道 ACK。

## 59. 回调金额不一致

立即：

- 不更新成功；
- 保存原始报文；
- 主动查渠道；
- 对比下单金额、渠道请求金额和回调金额；
- 检查币种和单位；
- 检查渠道应用或商户号；
- 升级安全事件。

不能：

- 以回调金额覆盖订单金额；
- 以本地金额强行忽略渠道结果。

## 60. 退款请求超时

处理：

```text
保持退款单 ING
→ 查询原退款单
→ 成功则补本地并累计退款
→ 失败则更新失败
→ 未知继续查
```

退还额度：

- 调用前预占；
- 成功后转为已退；
- 明确失败后释放；
- 未知时保持冻结。

## 61. 退款本地关闭但渠道成功

处理：

1. 暂停该支付单的新退款；
2. 查询渠道；
3. 恢复真实退款事实；
4. 更新退款单；
5. 回写支付单累计退款；
6. 补记退款账务；
7. 修正可退余额和结算余额；
8. 进入差错复盘。

## 62. 转账请求超时

处理：

```text
保持 ING
→ 查询原转账单
→ 明确成功更新并通知
→ 明确失败更新并通知
→ 未知继续查或人工核对
```

绝对禁止：

```text
超时 → 判失败 → 用新单号再次出款
```

## 63. 分账部分成功

处理：

- 父订单可能已经任务结束；
- 逐条查看分账记录；
- 成功记录不再重发；
- 失败记录重试；
- 已受理记录继续查询；
- 核对渠道账单；
- 检查已分账后退款。

## 64. MQ 消息重复

处理：

- 消息只是触发器；
- 业务处理前重新查数据库状态；
- 不信任消息中的旧状态；
- 使用 CAS 和唯一约束；
- 重复消息可以直接跳过。

## 65. MQ 消息丢失

兜底：

- 数据库状态扫描；
- 通知巡检；
- 分账超时扫描；
- Outbox 发布器；
- 人工补偿工具。

【背诵结论】

> MQ 只负责异步触发，数据库事实和外部查询负责恢复结果。任何资金消息都不能设计成“只消费一次，丢后就结束”。

# 第十四部分：幂等、并发和事务

## 66. 幂等的最终防线

优先级：

1. 数据库唯一约束；
2. 条件状态更新；
3. 行锁或额度冻结；
4. 幂等业务记录；
5. Redis 锁；
6. 前端防重。

越靠后越不能单独保障资金安全。

## 67. 支付幂等

唯一键：

```text
mch_no + mch_order_no
```

相同请求重试：

- 相同订单号和相同内容，返回已有订单；
- 相同订单号但金额不同，返回冲突；
- 不能生成第二笔支付。

## 68. 回调幂等

状态更新：

```text
UPDATE pay_order
SET state = SUCCESS
WHERE pay_order_id = ?
AND state = ING
```

如果更新 0 行：

- 可能已经成功；
- 可能已经失败；
- 可能已经关闭；
- 重新读取并判断，不盲目报错。

## 69. 退款并发

必须防止两个请求同时满足：

```text
可退余额足够
```

正确方案：

- 锁定支付单；
- 冻结退款额度；
- 唯一退款占用；
- 调渠道前提交本地预占；
- 成功后转已退款；
- 失败释放；
- 未知保持冻结。

## 70. 结算并发

防止同一账务事件进入两个结算单：

- 结算明细唯一占用；
- 结算批次输入水位固定；
- 同商户同周期幂等；
- 审批后不可重算覆盖；
- 重算生成新版本。

## 71. 出款并发

唯一键：

```text
settlement_order_id + account_id + currency
```

执行：

- 冻结可结算余额；
- 创建出款单；
- 调用渠道；
- 未知保持处理中；
- 成功扣减；
- 明确失败释放；
- 银行退票恢复应收。

## 72. 事务边界

不能在数据库事务中长时间等待渠道 HTTP。

推荐：

```text
事务1：创建订单/预占额度
事务外：调用渠道
事务2：根据明确结果更新
查询任务：处理未知结果
```

任何跨数据库和外部渠道流程都不能追求单事务强一致，而要通过状态机、幂等和补偿达到可控一致。

# 第十五部分：账务系统

## 73. 为什么支付订单不能当账

支付订单无法完整表示：

- 渠道应收；
- 商户应付；
- 平台手续费收入；
- 渠道成本；
- 退款负债；
- 商户可结算余额；
- 平台垫资；
- 差错挂账。

账务必须用复式记账。

基本规则：

```text
资产 = 负债 + 所有者权益
每张凭证：借方合计 = 贷方合计
```

## 74. 核心账户

| 账户 | 类型 | 含义 |
|---|---|---|
| 渠道清算应收 | 资产 | 渠道应给平台但未到账 |
| 银行存款 | 资产 | 实际收到的钱 |
| 商户待结算 | 负债 | 平台已欠商户但未释放 |
| 商户可结算 | 负债 | 可进入出款 |
| 商户冻结 | 负债 | 风控或退款冻结 |
| 手续费收入 | 收入 | 平台向商户收费 |
| 渠道成本 | 成本 | 支付机构收费 |
| 退款应付 | 负债 | 待退资金 |
| 商户欠款 | 资产 | 结算后退款等形成应收 |
| 差错挂账 | 资产或负债 | 待查资金 |

## 75. 支付成功示例

用户支付 100 元，商户手续费 0.60 元：

```text
借：渠道清算应收     100.00
    贷：商户待结算     99.40
    贷：手续费收入      0.60
```

如果平台只是代理，不控制交易本金，收入可能只确认服务费。必须按真实资金控制权和合同判断总额法或净额法。

## 76. 渠道结算到账

渠道扣 0.38 元成本后向平台到账 99.62 元：

```text
借：银行存款          99.62
借：渠道成本           0.38
    贷：渠道清算应收   100.00
```

平台向商户结算 99.40 元：

```text
借：商户待结算        99.40
    贷：银行存款       99.40
```

平台毛利为：

```text
0.60 - 0.38 = 0.22
```

## 77. 退款记账

结算前退款：

- 冲减商户待结算；
- 冲减渠道清算应收；
- 按合同决定手续费是否退回。

结算后退款：

- 优先从商户余额扣回；
- 余额不足形成商户欠款；
- 冻结后续结算；
- 必要时使用风险准备金；
- 增加新退款凭证，不修改原支付分录。

## 78. 账务事件

推荐事件：

```text
PAYMENT_SUCCEEDED
PAYMENT_FEE_CHARGED
REFUND_SUCCEEDED
DIVISION_SUCCEEDED
CHANNEL_SETTLED
SETTLEMENT_CREATED
PAYOUT_SUCCEEDED
PAYOUT_RETURNED
MANUAL_ADJUSTED
```

事件唯一键必须覆盖：

```text
事件类型 + 来源系统 + 来源交易号 + 版本
```

## 79. 账务不可变原则

- 分录只新增，不修改；
- 不删除历史分录；
- 错误通过反向分录冲正；
- 调账需审批和原因；
- 余额是分录的汇总结果；
- 每日检查借贷平衡；
- 账务事件重复消费不能重复记账。

【背诵结论】

> 订单记录业务状态，分录记录资金价值。支付成功不自动等于已经记账，账务错误不能修改历史，只能冲正。

第十六部分：清分、结算、出款

## 80. 清分

清分负责计算各方应收应付。

输入：

- 已确认支付；
- 已确认退款；
- 商户手续费；
- 渠道成本；
- 分账；
- 冻结和预留；
- 调账；
- 账期。

输出：

- 商户应收；
- 服务商收益；
- 平台手续费收入；
- 渠道成本；
- 分账接收方金额。

公式：

```text
商户收入
= 支付金额
- 商户手续费
- 退款
- 分账
- 冻结/预留
+ 调账
```

## 81. 结算

结算负责把可结算资金按账期释放。

结算资格：

- 支付成功；
- 已完成对账；
- 不在退款风险窗口；
- 未被冻结；
- 达到账期；
- 未被其他结算单占用；
- 商户和结算账户正常。

结算金额：

```text
本期应结
= 本期支付成功
- 手续费
- 退款
- 分账
- 风险预留
- 上期负余额
+ 调整
```

## 82. 结算单状态

推荐：

```text
CREATED
→ CALCULATED
→ REVIEWING
→ APPROVED
→ PAYOUT_PENDING
→ PAYING
→ SUCCESS
```

异常：

```text
CALC_FAILED
REJECTED
PAYOUT_FAILED
PAYOUT_UNKNOWN
PARTIALLY_RETURNED
CLOSED
```

## 83. 结算幂等

必须防止：

- 同一支付进入两个结算单；
- 同一退款重复扣减；
- 结算任务重复生成；
- 出款超时重复打款。

关键唯一键：

```text
账务事件唯一
结算批次唯一
结算明细唯一占用
出款指令唯一
```

## 84. 出款

出款流程：

```text
结算单审批
→ 冻结可结算余额
→ 创建出款单
→ 调银行或转账渠道
→ 明确成功/失败/未知
→ 未知继续查询
→ 银行回单确认
→ 释放或扣除余额
```

出款状态：

```text
INIT
PROCESSING
SUCCESS
FAIL
UNKNOWN
RETURNED
```

【背诵结论】

> 清分算应收应付，记账记录债权债务，结算生成可出款单据，出款实际划拨资金，银行回单最终确认到账。

# 第十七部分：对账和差错

## 85. 对账是什么

对账是比较两个独立事实源。

常见：

- 支付中心本地记录；
- 渠道账单；
- 账务分录和余额；
- 银行流水；
- 结算和出款回单。

## 86. 对账层次

1. 交易对账；
2. 退款对账；
3. 转账和分账对账；
4. 账务与业务对账；
5. 账务与银行资金对账；
6. 结算和出款对账；
7. 商户账单核对。

## 87. 对账批次

要有：

- 渠道；
- 业务日；
- 文件哈希；
- 文件完整性；
- 本地笔数和金额；
- 渠道笔数和金额；
- 匹配数；
- 差异数；
- 批次状态；
- 操作审计。

对账批次必须支持重复执行且结果幂等。

## 88. 匹配顺序

```text
渠道订单号
→ 平台订单号
→ 商户订单号 + 金额
→ 其他辅助字段
```

辅助字段匹配只能视为较低置信度，不能直接自动修复资金。

## 89. 对账差异分类

- 本地有、渠道无；
- 渠道有、本地无；
- 状态不一致；
- 金额不一致；
- 手续费不一致；
- 币种不一致；
- 退款不一致；
- 重复记录；
- 时间跨期；
- 无法识别。

## 90. 对账处理原则

1. 原始账单不可修改；
2. 差异不能直接覆盖订单；
3. 先查渠道事实；
4. 区分自动修复和人工处理；
5. 修复业务状态；
6. 生成账务调整；
7. 复核借贷和资金；
8. 记录责任人和关闭时间。

【背诵结论】

> 对账负责发现不一致，不负责无脑修改订单。差异必须先分类、取证、确认责任，再决定补单、退款或调账。

## 91. 日切

日切是按业务规则切分账务日期。

必须明确：

- 时区；
- 日切时间；
- 支付成功归属；
- 退款归属；
- 跨日回调；
- 渠道账单口径；
- 节假日；
- 迟到交易。

同一交易应保存：

```text
交易时间
渠道成功时间
账务日期
结算周期
```

## 92. 差错工单

工单至少包含：

```text
差错编号
类型
严重级别
商户
平台订单号
渠道订单号
差异金额
渠道证据
当前状态
负责人
处理动作
截止时间
关闭时间
```

状态：

```text
OPEN
→ INVESTIGATING
→ WAITING_CHANNEL
→ WAITING_MERCHANT
→ APPROVED_FIX
→ FIXED
→ CLOSED
```

# 第十八部分：并发、高可用和线上问题

## 93. 高并发核心原则

1. 先保证唯一性，再优化性能；
2. 外部渠道调用不能包在长事务里；
3. 同一交易只使用一个稳定幂等键；
4. 余额不能只靠先查后改；
5. 热点账户要分片或按明细汇总；
6. MQ 必须可重复消费；
7. 定时任务必须可重复执行；
8. 限流必须按租户和渠道隔离；
9. 故障时优先保护资金安全；
10. 所有修复必须可审计。

## 94. 渠道超时和重试

可以重试：

- 查询；
- 关单；
- 通知；
- 在明确幂等前提下的创建和退款。

不能无脑重试：

- 新单号重新支付；
- 新单号重新退款；
- 新单号重新出款；
- 金额不一致的请求；
- 明确不可恢复的业务错误。

重试策略：

- 指数退避；
- 加随机抖动；
- 最大次数；
- 最大时间；
- 持久化下次执行时间；
- 未知状态升级。

## 95. 熔断和隔离

- 每个渠道独立超时；
- 每个渠道独立连接池；
- 下单、查单、通知线程池隔离；
- 某渠道故障不能拖垮全部交易；
- 熔断只阻止新建调用，不丢失原渠道未知单；
- 已进入未知的交易继续查原渠道。

## 96. MQ 可靠性

必须处理：

- 重复投递；
- 延迟；
- 丢失；
- 消费失败；
- 消费线程阻塞；
- 消息顺序；
- 积压；
- 发布成功但数据库失败；
- 数据库成功但发布失败。

推荐：

- 业务事实落库；
- Outbox 事件；
- 消费者幂等；
- 定时扫描；
- 死信告警；
- 人工补偿工具。

## 97. Jeepay 定时任务注意事项

【Jeepay 现状】

支付补单、过期、退款查单、退款过期、转账查单、分账查单均为每分钟执行。

当前代码没有明确的分布式任务锁。

多实例部署风险：

- 同一订单被多个实例扫描；
- 渠道查询放大；
- 通知重复发送；
- 分账任务重复触发。

生产必须：

- 分布式调度；
- leader election；
- 行级领取；
- 分片扫描；
- 处理幂等；
- 记录任务水位。

## 98. 线上故障排查顺序

### 支付不出参数

检查：

- 参数和签名；
- 商户和应用；
- 路由；
- 渠道配置；
- 渠道返回；
- 结果是否未知。

### 支付一直 `ING`

检查：

- 回调；
- 查单；
- MQ；
- 定时任务；
- 本地 SQL；
- 渠道真实状态。

### 支付成功但商户未收到

检查：

- 通知记录；
- URL；
- HTTP 响应；
- 重试；
- MQ；
- 线程池；
- 商户业务幂等。

### 退款不成功

检查：

- 原支付状态；
- 可退余额；
- 在途退款；
- 商户退款单号；
- 渠道配置；
- 退款渠道状态。

### 转账成功但商户说没到

检查：

- 渠道成功还是仅受理；
- 收款账户；
- 银行回单；
- 是否退票；
- 渠道账单。

### 账务不平

检查：

- 业务事件是否重复；
- 分录借贷是否相等；
- 凭证是否重复；
- 余额汇总是否滞后；
- 调账是否审批；
- 对账差异是否未入账。

## 99. 线上改数据原则

尽量不直接改：

- 订单状态；
- 退款金额；
- 账务分录；
- 余额；
- 结算单；
- 出款单。

必须提供受控操作：

- 补单；
- 冲正；
- 重发通知；
- 重跑对账；
- 释放冻结；
- 生成调账。

每次操作记录：

```text
操作人
审批人
原因
操作前状态
操作后状态
关联工单
时间和 IP
```

# 第十九部分：安全、风控和合规

## 100. 接口安全

- 签名；
- 时间戳；
- nonce；
- 防重放；
- 限流；
- 请求大小限制；

- 不写日志；
- 不直接提交源码。

## 102. SSRF

商户通知 URL 由外部输入，支付中心会主动 POST。

必须阻止：

- `127.0.0.1`；
- 内网网段；
- 云元数据地址；
- 非允许端口；
- DNS 重绑定；
- 恶意重定向；
- 超大响应。

## 103. 风控

至少关注：

- 单笔限额；
- 日累计；
- 月累计；
- 高频交易；
- 异常退款率；
- 异常拒付率；
- 同设备多商户；
- 同账户多身份；
- 黑名单；
- 商户经营异常；
- 结算账户变更。

## 104. 合规边界

Jeepay 是技术系统，不自动提供支付业务许可证。

必须明确：

- 谁收单；
- 资金进入谁账户；
- 谁向商户结算；
- 是否符合资金存管要求；
- 是否存在无资质二次清分；
- 商户实名和准入是否完成；
- 分账是否由持牌机构实际执行。

【背诵结论】

> 技术上能归集和分账，不代表业务上可以无证从事清结算。支付工程师必须理解系统能力与法律、合同、资金存管边界。

# 第二十二部分：Jeepay 当前风险清单

## 111. 需要背下来的实现边界

1. 支付订单 `CANCEL=4` 当前未写入。
2. 转账 `CLOSED=4` 当前没有过期任务写入。
3. 支付过期任务直接关闭 `INIT/ING`，未先确认渠道关闭。
4. 支付回调主体只明确处理 `ING`。
5. `SYS_ERROR` 可能让订单停在 `INIT`，常规补单只扫描 `ING`。
6. MQ 查单首次延迟 5 秒，单链最多 6 次。
7. 支付定时补单扫描创建超过 10 分钟的 `ING`。
8. 退款补单每分钟扫描 `ING`；转账补单只扫描最近一天内的 `ING`。
9. 退款默认两小时过期，过期任务直接改 `CLOSED`。
10. 自动分账延迟 80 秒。
11. 分账已受理超过 5 分钟后查询。
12. 通知默认最多 6 次。
13. 通知响应必须为 `SUCCESS`。
14. 通知 HTTP 超时为 20 秒。
15. `notify_state=1` 只表示开始发送，不表示发送成功。
16. 支付失败路径没有直接商户异步通知。
17. 商户查询接口主要查本地订单。
18. `t_order_snapshot` 是预留表，当前代码未写入。
19. 数据库没有物理外键。
20. 路由表允许多个通道，但当前没有权重、成功率和故障转移算法。
21. 配置使用本地内存缓存，依赖 MQ 刷新。
22. MQ 线程池为共享配置，通知慢请求可能阻塞其他任务。
23. 定时任务当前没有明确分布式锁。
24. 退款“先查在途再调渠道”存在并发窗口。
25. 转账没有余额、冻结和完整出款账务。
26. 分账父状态结束不等于所有明细成功。
27. Jeepay 没有完整对账、复式记账、清分和结算。
28. 支付签名当前使用 MD5 兼容方案。
29. 通知 URL 当前仅做协议校验，生产需防 SSRF。
30. 仓库只有少量兼容性和冒烟测试，没有核心资金场景自动化测试。

【背诵结论】

> Jeepay 能证明支付主链路的基本设计，但不能仅凭现有代码就宣称达到生产级资金系统。面试中应主动说明交易实现和生产补强边界。

# 第二十三部分：与资深工程师沟通

## 112. 标准表达

### 描述未知

> 渠道调用超时，当前是结果未知，不是失败。我会保持订单处理中，按原平台订单号查询渠道，不会换单号重新下单。

### 描述支付成功

> 支付状态已明确成功，接下来还要确认商户通知、账务事件和自动分账是否完成。

### 描述通知失败

> 支付已经成功，商户通知尚未成功。通知记录仍可重试，不能通过回滚支付状态解决。

### 描述退款未知

> 退款请求已被渠道受理，当前退款单为处理中。需要查询原退款单，并保持退款额度冻结。

### 描述转账

> 转账单是渠道出款交易，不等于结算单。出款超时时要先查原转账单，防止重复出款。

### 描述分账

> 父订单分账任务结束，但明细可能部分成功、部分失败或已受理，需要逐条核对。

### 描述对账差异

> 当前存在渠道有本地无的记录，我会先核对文件完整性、渠道订单号和金额，再分类处理，不会直接创建或覆盖订单。

### 描述账务差异

> 历史分录不修改，通过新增冲正凭证修复；修复后重新核对借贷平衡、账户余额和资金流水。

## 113. 不要说错的话

错误：

> 回调把订单改成支付中。

正确：

> 回调把支付中的订单收敛为成功或失败。

错误：

> 支付超时了，所以失败。

正确：

> 请求超时，结果未知，需要按原单查询。

错误：

> 支付成功就是结算成功。

正确：

> 支付成功只是交易事实，结算还要经过对账、清分、记账和出款。

错误：

> 分账完成了就全部到账。

正确：

> 分账任务结束不代表所有接收方成功，也不代表结算到账。

错误：

> MQ 保证只消费一次。

正确：

> MQ 通常至少一次投递，业务必须幂等。

# 第二十四部分：高频问答

## 114. 为什么渠道超时不能判失败

因为请求可能到达渠道并成功，只是响应丢包。直接判失败并重新下单可能重复扣款。

## 115. 为什么先落库再调用渠道

为了固定平台订单号、支持幂等、保存回调关联和超时查询依据。

## 116. 为什么支付单不能和渠道形成事务

渠道是外部系统，无法参与本地数据库事务，必须通过状态机、查询、补偿和对账保证一致。

## 117. 为什么回调必须验签

回调查询地址可能公开，攻击者可以伪造成功回调。验签确认来源，业务字段校验确认是这笔订单。

## 118. 为什么验签通过还要校验金额

签名只证明报文由持证主体发出，不能证明应用、订单和金额与本地上下文匹配。

## 119. 为什么通知必须幂等

通知可能重复、超时后重试、MQ 重复消费。商户不能重复发货或重复入账。

## 120. 为什么退款必须独立订单

支付和退款是一对多关系，每次退款有独立金额、渠道状态、失败原因和通知。

## 121. 为什么全额退款修改支付状态

`REFUND` 表示原交易仍然成功但已全部退回，便于统计、风控和后续不可继续退款判断。

## 122. 为什么每次退款成功后更新累计金额

累计金额是后续可退额度和全额退款判断的唯一基础，必须在数据库事务中原子更新。

## 123. 为什么转账不能复用退款

退款必须原路返回原支付单；转账是独立的指定账户出款，资金和合规风险不同。

## 124. 为什么分账父状态不能代表明细成功

一次任务可以有多个接收方，每个接收方独立调用和返回，必须按记录管理。

## 125. 为什么支付查询不一定是渠道查询

商户查询接口主要读取 Jeepay 本地记录，内部补单才调用渠道真实查询。

## 126. 为什么支付成功后还要对账

回调可能丢失、延迟、乱序或错误；对账可以发现本地和渠道的最终差异。

## 127. 为什么对账不直接修订单

差异原因可能是账单延迟、订单号错配、重复文件、渠道错误或本地错误。直接覆盖会破坏审计。

## 128. 为什么账务需要复式记账

支付单只表示交易状态，无法完整表示资产、负债、收入和成本。复式记账保证每笔价值变化有对应来源和去向。

## 129. 为什么历史分录不能修改

修改历史会破坏审计和可追溯性。错误应通过反向分录冲正。

## 130. 为什么结算与支付必须分离

支付成功不等于已经对账、过了冻结期和满足账期。结算要使用账务和清分结果。

## 131. 为什么出款还需要银行回单

渠道或银行接口成功可能只是受理，实际到账可能失败或退票。

# 第二十六部分：最终背诵稿

## 137. 三分钟口述版

Jeepay 支付中心先根据商户号和应用 ID 识别调用主体，用应用密钥验签，再按商户、应用和 `wayCode` 查路由，得到实际 `ifCode` 和商户费率。系统生成平台支付单号和费率快照，以 `INIT` 落库后调用渠道。渠道明确成功或失败进入终态；处理中、超时或结果未知进入 `ING`。如果已经拿到二维码或 `prepay_id`，可以返回商户让用户付款；如果没拿到支付参数，只能后台按原订单号查单。渠道回调和主动查询通过旧状态条件更新把 `ING` 收敛到 `SUCCESS/FAIL`，重复回调不会重复迁移状态。

支付成功后创建商户通知记录，异步通知失败会按延迟策略重试，通知成功不等于支付成功，通知失败也不能回滚支付。支付启用自动分账时，成功后延迟触发分账。分账父任务结束只表示本轮结束，具体接收方要看分账明细。

退款必须是独立订单，必须关联原支付单并使用原渠道。退款前检查剩余可退金额和在途退款，退款成功后才累计支付单已退金额；部分退款保持支付成功，全额退款把支付状态改为 `REFUND`。退款超时属于未知，必须查询原退款单，不能重复退款。

转账是独立出款交易，不是退款。转账超时可能已经出款，必须查询原转账单，不能换单号重发。

支付、退款、转账通过唯一商户单号防重，状态迁移通过数据库条件更新防并发，通知通过订单号加类型唯一记录防重复。MQ 和定时任务只是异步触发与兜底，最终事实仍要从数据库和渠道确认。支付成功、通知成功、账务入账、清结算完成是四个不同事实。

生产结算还要以渠道账单与本地交易对账，处理差异后清分、复式记账、生成可结算余额和结算单，再执行出款并核对银行回单。对账差异不能直接覆盖订单，账务错误不能修改历史分录，只能通过冲正和调账修复。

## 138. 最浓缩一句话

> 支付中心先把请求变成可信、幂等、可查询的本地交易，通过回调和查单收敛渠道结果，再可靠通知商户；结算系统再基于已确认、已对账、已记账的事实计算各方应收应付，完成结算、出款和资金核对。
