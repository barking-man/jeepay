# Jeepay 支付系统高可用、高性能与异常兜底设计详解

## 文档定位

本文回答三个问题：

1. Jeepay 当前代码到底具备哪些高可用和一致性能力；
2. 哪些地方只是“能补偿”，但还不是真正生产级高可用；
3. 要把 Jeepay 建设成支付结算系统，还需要补什么。

标记说明：

- `【Jeepay 现状】`：当前代码或配置真实存在的能力；
- `【当前不足】`：当前实现不足以支撑生产高可用的地方；
- `【生产方案】`：二次开发建议；
- `【核心结论】`：可直接背诵的结论。

---

# 一、先理解支付系统的高可用

支付系统的高可用不是“服务进程不挂”，而是同时满足：

```text
服务可用
+ 交易不重复
+ 状态可恢复
+ 资金不丢失
+ 数据可对账
+ 故障可定位
+ 结果可补偿
+ 热点可扩展
```

支付系统真正困难的不是 QPS，而是在高并发和故障情况下仍然保证资金正确。

高可用必须同时依靠：

1. 应用多实例；
2. 数据库、Redis、MQ 的高可用；
3. 请求超时和隔离；
4. 幂等和状态机；
5. 异步消息补偿；
6. 定时扫描兜底；
7. 对账和差错处理；
8. 监控、告警、容量治理；
9. 可回滚、可灰度的发布流程。

【核心结论】

> 多部署几个支付服务实例，只能解决进程单点，不能解决重复支付、状态丢失、消息丢失、重复出款和账实不符。支付高可用必须以资金正确为中心。

# 二、Jeepay 当前架构中的高可用基础

## 1. 服务和模块拆分

Jeepay 包含：

- `jeepay-payment`：支付网关；
- `jeepay-merchant`：商户后台；
- `jeepay-manager`：运营后台；
- `jeepay-service`：业务服务和数据库访问；
- `jeepay-core`：公共模型和工具；
- MQ、OSS 公共组件。

支付网关、商户后台和运营后台分开，意味着某个后台查询压力不会直接占满支付网关进程。

【Jeepay 现状】

从应用结构上可以部署多个支付网关实例。

【当前不足】

仓库没有完整给出生产级集群治理、负载均衡、健康检查、优雅停机和跨机房方案。

【生产方案】

- 网关无状态化；
- 多实例部署；
- 健康检查；
- 优雅停机；
- 滚动发布；
- 按接口和租户限流；
- 与后台管理流量隔离。

## 2. 数据库唯一约束

Jeepay 依靠唯一键防止核心重复交易：

```text
支付：mch_no + mch_order_no
退款：mch_no + mch_refund_no
转账：mch_no + mch_order_no
通知：order_id + order_type
```

唯一约束是幂等的最后防线，比 Redis 锁更可靠。

## 3. 状态条件更新

支付、退款、转账和分账的状态更新都带有旧状态条件：

```text
INIT → ING
ING → SUCCESS / FAIL / CLOSED
```

这相当于数据库 CAS。

好处：

- 重复回调只有一个能成功推进；
- 回调和主动查询并发时不会重复迁移；
- 已终态订单不会被旧消息覆盖。

## 4. Redis

Jeepay 使用 Redis 支撑：

- 后台登录 token；
- token 有效期；
- 图片验证码；
- 部分缓存能力。

【当前不足】

- 支付业务的核心正确性不能依赖 Redis；
- Redis 故障时后台登录会受影响；
- 当前没有看到统一的高可用 Redis 使用规范、熔断和降级策略；
- 不应把 Redis 锁作为唯一防重措施。

## 5. MQ

Jeepay 支持：

- RocketMQ；
- ActiveMQ；
- RabbitMQ；
- 阿里云 RocketMQ。

MQ 用于：

- 支付延迟查单；
- 商户通知；
- 自动分账；
- 配置缓存刷新；
- 登录缓存清理。

MQ 提供了异步和削峰能力。

【当前不足】

- 没有事务消息或统一 Outbox；
- 多个业务共用同一个异步线程池；
- MQ 失效时部分流程只能依赖数据库扫描；
- 通知和分账没有完整死信处理平台。

## 6. 定时补偿

当前每分钟执行：

- 支付补单；
- 退款补单；
- 转账补单；
- 分账受理查询；
- 支付过期；
- 退款过期。

【当前不足】

代码中没有发现统一的分布式任务锁。

多实例部署时，每个实例都可能执行同一批扫描。

# 三、Jeepay 当前的幂等体系

## 1. 支付下单幂等

商户维度唯一：

```text
mch_no + mch_order_no
```

【Jeepay 现状】

重复商户订单号通常返回“订单已存在”。

【当前不足】

没有完整保存首次请求摘要和首次响应，重复请求不一定会返回原支付参数。

【生产方案】

相同幂等键、相同请求：

```text
返回原平台订单号和当前状态
```

相同幂等键、不同金额或不同支付方式：

```text
返回幂等冲突
```

## 2. 支付回调幂等

状态条件更新：

```text
WHERE pay_order_id = ?
AND state = ING
```

更新行数为 0 时不重复执行成功副作用。

## 3. 通知幂等

通知记录唯一：

```text
order_id + order_type
```

重复成功回调不能重复创建第二条通知。

## 4. 退款幂等

商户退款单号唯一：

```text
mch_no + mch_refund_no
```

退款成功时，退款单状态和支付单累计退款字段在同一事务中更新。

【当前不足】

在调用渠道前，对并发退款额度的预占不够强。

【生产方案】

新增退款额度冻结或支付单行锁。

## 5. 转账幂等

转账商户订单号唯一。

【当前不足】

- 没有商户余额冻结；
- 没有完整出款账务；
- 超时后依赖查询；
- 超过一天仍未知的转账不再被自动扫描。

## 6. 分账幂等

分账父订单和每条记录使用状态条件更新。

失败重发时会生成新的系统分账批次号。

【当前不足】

父任务异常可能停留在处理中；

已受理查询没有明确最大次数。

## 7. 账务幂等

【Jeepay 现状】

Jeepay 没有完整账务模块。

【生产方案】

账务事件：

```text
event_type + source_type + source_id + source_version
```

必须唯一。

同一支付、退款、分账、结算事件只能生成一次有效凭证。

【核心结论】

> 支付幂等靠商户订单号，回调幂等靠状态 CAS，通知和账务幂等靠业务唯一键。Redis 锁不能替代数据库约束。

# 四、Jeepay 是否需要分布式锁

## 1. 当前结论

【Jeepay 现状】

当前代码中未发现统一的分布式任务锁或 Redisson、ShedLock 等机制。

这并不意味着所有接口都不安全，因为很多交易状态依靠数据库 CAS 和唯一约束。

但多实例定时任务会产生：

- 重复扫描；
- 重复渠道查询；
- 重复通知尝试；
- 重复分账触发；
- 无意义的数据库和渠道压力。

## 2. 哪些地方适合分布式锁

适合：

- 分钟级补单任务选主；
- 日终对账任务选主；
- 结算批次生成；
- 出款批次执行；
- 热点账户余额冻结；
- 配置缓存重建；
- 低频全局任务。

## 3. 哪些地方不能只靠分布式锁

不能只靠：

- 支付回调状态更新；
- 退款成功回写；
- 通知唯一性；
- 分账记录最终状态；
- 账务入账；
- 结算明细归属。

这些必须继续使用数据库唯一约束和 CAS。

原因：

- Redis 锁可能过期；
- 进程可能在持锁期间停顿；
- 网络分区可能让两个实例都以为拿到锁；
- 锁释放可能误删别人的锁。

## 4. Redis 锁的基本安全要求

至少：

```text
SET lock_key owner_token NX PX lease_time
```

释放时比较 owner token 后删除，不能直接 DEL。

长时间任务需要续租。

更重要的是：

```text
锁负责减少并发
数据库约束负责最终正确
```

## 5. 理想的分布式任务方案

- 任务调度平台统一分配；
- leader election；
- 数据库抢占任务；
- 每次只领取一批记录；
- 记录 owner 和 lease；
- 任务处理幂等；
- 失败自动释放；
- 有超时恢复。

【核心结论】

> Jeepay 当前依赖数据库 CAS 保障重复回调的大部分幂等，但缺少分布式任务锁。生产环境应增加任务选主或数据库任务领取，不能把 Redis 锁当成资金一致性的唯一保证。

# 五、异常兜底体系

## 1. 渠道超时

处理：

```text
订单进入 ING
→ 按原平台订单号查原渠道
→ 成功、失败或继续等待
```

不能：

- 直接判失败；
- 换平台单号重下；
- 换渠道新建交易。

## 2. 渠道返回未知

- 保留 `ING`；
- 延迟 MQ 查询；
- 定时任务持续兜底；
- 超过阈值告警；
- 日终对账。

## 3. 支付中心系统异常

【Jeepay 现状】

- 可能保留 `INIT`；
- 常规补单只扫描 `ING`；
- `INIT` 可能最终过期关闭。

【生产方案】

- 记录异常阶段；
- 已调用渠道后明确标记结果未知；
- 主动查询原渠道；
- 建立异常队列；
- 超期人工处理。

## 4. 数据库提交成功，消息没有发出

【Jeepay 现状】

存在这个事务空档。

【生产方案】

Outbox：

```text
业务状态更新
+ outbox 事件
在同一数据库事务提交
→ 发布器扫描并投递 MQ
```

## 5. MQ 重复

消费者必须：

- 重新读取数据库状态；
- 使用业务唯一键；
- 使用 CAS；
- 不信任消息里的旧状态。

## 6. MQ 延迟

- 监控积压；
- 通知和分账使用定时巡检；
- 不在业务线程无限等待；
- 延迟超过阈值升级。

## 7. MQ 丢失

- Outbox 扫描重发；
- 数据库状态任务扫描；
- 死信补偿；
- 人工重放。

## 8. Redis 故障

- 后台鉴权可拒绝访问；
- 支付主链路不能依赖 Redis 才能保证交易正确；
- 本地缓存必须能回源数据库；
- 热点 key 需要防击穿；
- 缓存不可用时优先保护交易主链。

## 9. 配置缓存不一致

Jeepay 支持关闭配置缓存，改为直接查询数据库；配置变化通过 MQ 通知刷新。

【当前不足】

- 多实例必须全部收到刷新消息；
- 缓存没有统一 TTL 和版本机制时，可能出现不同实例行为不同。

【生产方案】

- 配置版本号；
- 本地短 TTL；
- MQ 广播；
- 定时全量校准；
- 密钥轮换双版本；
- 停用商户快速失效。

## 10. 通知失败

Jeepay：

- 默认最多 6 次；
- 30、60、90、120、150 秒递进；
- 20 秒 HTTP 超时；
- 人工重发失败记录。

【当前不足】

没有独立扫描长期“通知中”记录的定时任务。

【生产方案】

- 通知巡检；
- MQ 死信；
- 域名健康检查；
- 按商户限流；
- 独立通知线程池；
- 防止 SSRF。

## 11. 退款超时

- 保持退款单 `ING`；
- 按原退款单查询；
- 冻结退款额度；
- 未知时不能再次退款；
- 超期告警。

## 12. 转账超时

- 保持 `ING`；
- 按原转账单查询；
- 明确失败后才能重发；
- 超过一天未知需人工处理；
- 不得换单号重复出款。

## 13. 本地关闭但渠道成功

处理：

```text
验签
→ 查渠道
→ 保存晚到支付异常
→ 查询商户履约
→ 补履约或退款
→ 补账务
→ 日终对账
```

## 14. 对账差异

- 不直接覆盖业务订单；
- 先确认账单完整性；
- 分类差异；
- 自动修复只限低风险场景；
- 大额、金额不一致和已结算差异必须人工处理。

【核心结论】

> 支付高可用依靠“状态机 + 数据库约束 + 重试 + 查询补偿 + Outbox + 对账”多层防线，不能只靠某一种重试或某个中间件。

# 六、当前线程池和隔离风险

【Jeepay 现状】

MQ 组件使用一个共享执行器，当前配置为：

```text
核心线程：20
最大线程：300
队列：10
拒绝策略：CallerRunsPolicy
```

该执行器同时承担多个 MQ 接收任务。

商户通知 HTTP 超时为 20 秒。

【风险】

- 通知慢接口可能占满线程；
- 其他 MQ 任务被阻塞；
- CallerRunsPolicy 会让 MQ 接收线程执行任务；
- 300 个线程不一定更快，反而会增加上下文切换；
- 队列只有 10，容易快速触发拒绝；
- 单个商户可能形成通知热点。

【生产方案】

- 通知、支付查单、退款查单、分账使用独立线程池；
- 按渠道隔离；
- 队列容量压测后确定；
- 设置最大并发；
- 商户级限流；
- 监控活跃线程、排队时间和拒绝次数；
- 通知发送改为独立调度或异步网关。

# 七、高可用架构建议

## 1. 应用层

- 支付网关多实例；
- 无本地会话依赖；
- 健康检查；
- 优雅停机；
- 滚动发布；
- 版本兼容；
- 接口限流；
- 渠道隔离。

## 2. 数据库

- 主从或集群；
- 自动故障转移；
- 唯一索引；
- 读写分离；
- 慢 SQL 监控；
- 备份和恢复演练；
- 大表分区和归档；
- 核心资金写入以主库为准。

## 3. Redis

- 高可用部署；
- 超时和熔断；
- 缓存不可用时允许回源；
- 不用 Redis 保存唯一资金事实；
- key 设计避免大 key 和热 key。

## 4. MQ

- 多副本；
- 生产重试；
- 消费幂等；
- 死信队列；
- 积压告警；
- 延迟消息可恢复；
- 关键事件有数据库 Outbox。

## 5. 渠道

- 独立连接池；
- 独立线程池；
- 连接超时、读超时、总 deadline；
- 熔断；
- 限流；
- 灰度切换；
- 原渠道未知单查询；
- 证书和密钥轮换。

## 6. 数据

- 交易、账务、对账分别治理；
- 资金数据长期保留；
- 操作日志和状态迁移审计；
- 原始渠道响应脱敏留存；
- 备份密钥和证书。

# 八、高性能设计

## 1. 不对渠道做长事务

正确顺序：

```text
本地创建订单
→ 提交事务
→ 调用渠道
→ 新事务更新结果
```

不能在一个数据库事务中等待渠道网络响应。

## 2. 异步化

适合异步：

- 商户通知；
- 自动分账；
- 补单扫描；
- 对账；
- 报表；
- 非关键查询。

不能异步跳过：

- 金额校验；
- 防重复；
- 状态 CAS；
- 资金冻结。

## 3. 缓存

适合缓存：

- 商户和应用基础配置；
- 服务商配置；
- 渠道路由；
- 支付产品字典。

风险：

- 密钥更新后必须失效；
- 商户停用必须快速生效；
- 缓存击穿；
- 不同实例数据不一致。

## 4. 数据库优化

- 支付查询按 `mch_no + created_at`；
- 补单按 `state + created_at`；
- 退款按 `pay_order_id + state`；
- 通知按 `state + last_notify_time`；
- 分账按 `pay_order_id/state/batch_order_id`。

当前初始化 SQL 对这些高频任务查询的索引并不完整。

## 5. 分页

避免深分页：

```text
LIMIT 100000, 100
```

采用：

- 主键游标；
- 时间窗口；
- ID 范围；
- 分片扫描；
- 小批次提交。

当前支付、退款、转账和分账定时扫描都使用页码分页。处理过程中结果集减少时，可能出现跳过记录的边界问题。

## 6. 热点账户

不要对单个商户余额行进行无限高频更新。

方案：

- 先写余额变动明细；
- 按账户分片；
- 按日期分桶；
- 异步汇总；
- 定期从分录重算余额。

## 7. 渠道流量治理

- 按渠道独立限流；
- 按商户独立配额；
- 按接口设置不同并发；
- 查询流量和下单流量分离；
- 交易高峰禁用低频批量任务；
- 通知失败不能拖垮支付。

## 8. 对账批处理

- 小批次读取；
- 游标分页；
- 文件流式解析；
- 本地和渠道数据建立索引；
- 差异落表而不是只写日志；
- 任务可重跑；
- 分片执行。

# 九、主要线上故障与处理

## 1. 支付成功率突然下降

排查：

- 是否单一渠道；
- 渠道超时率；
- 错误码分布；
- 数据库连接池；
- Redis 或配置问题；
- 限流或熔断；
- 发布变更。

处理：

- 停止故障渠道新建流量；
- 未知订单保留原渠道查询；
- 不在渠道故障时强制切换已调用交易；
- 对商户返回明确状态。

## 2. 大量支付处于 ING

- 检查 MQ 消费；
- 检查定时任务是否运行；
- 检查渠道查询是否超时；
- 按渠道、创建时间分批查询；
- 过旧未知订单进入人工队列。

## 3. 重复支付风险

- 按商户订单号查询原交易；
- 强制同一业务键；
- 禁止调用方自行生成新平台单号重试；
- 对重复支付建立核对和退款流程。

## 4. 重复退款风险

- 冻结退款额度；
- 查询原退款单；
- 未知状态不重复退款；
- 禁止并发退款和撤销。

## 5. 重复出款风险

- 出款调度加锁；
- 冻结余额；
- 唯一出款业务键；
- 查询原出款单；
- 未知状态转人工。

## 6. MQ 积压

- 判断消息类别；
- 降低非核心任务；
- 扩容消费者前确认 DB 和渠道容量；
- 不允许直接丢弃资金消息；
- 恢复后幂等补消费。

## 7. 通知大面积失败

- 判断单个商户还是全局；
- 检查网络和 DNS；
- 暂停高成本重试；
- 保留通知记录；
- 恢复后分批补发。

## 8. 配置缓存异常

- 核对数据库配置；
- 检查刷新消息；
- 确认所有实例版本；
- 临时关闭配置缓存；
- 修复后重新广播。

# 十三、支付系统高可用最难的十个点

## 1. 外部渠道无法和本地数据库组成事务

渠道已经成功，本地可能失败；本地成功，渠道可能未完成。

只能通过状态机、查单、补偿和对账解决。

## 2. 恰好一次消费不存在

MQ 是至少一次，必须依赖幂等。

## 3. 未知状态多于简单成功和失败

超时、处理中、响应丢失、报文异常都必须单独处理。

## 4. 回调乱序

回调顺序不可信，必须以渠道最终查询和账单为准。

## 5. 重复资金动作

重复支付、退款、出款、记账都会造成真实损失。

## 6. 热点账户

单个商户或平台账户可能成为数据库锁热点。

## 7. 渠道差异

每个渠道的状态码、幂等规则、回调协议和账单格式不同。

## 8. 事件最终一致性

状态、通知、分账、账务、结算可能短暂不一致，但必须可控和可恢复。

## 9. 人工操作风险

直接改订单、余额和分录可能破坏审计和资金一致性。

## 10. 故障时仍要保证资金安全

宁可保持未知并继续核对，也不能为了表面成功率错误判定失败或重复出款。

# 十四、标准口述总结

> Jeepay 当前已经具备支付状态 CAS、商户订单唯一约束、回调验签、主动查单、延迟 MQ、分钟级补单和通知重试，这些是交易可靠性基础。但它没有完整的分布式任务锁、Outbox、熔断限流、事务消息、核心账务和全链路可观测体系，多实例和长期未知场景仍有明显风险。生产化建设应以资金正确为第一目标：支付、退款、转账和结算使用稳定业务幂等键，状态更新使用 CAS，任务使用分布式领取并保持幂等，数据库状态和 MQ 之间使用 Outbox，未知交易按原渠道查询，超过阈值进入异常队列，最终通过渠道账单对账闭环。高可用不是单纯堆实例，而是服务冗余、状态机、幂等、隔离、限流、补偿、对账和监控共同组成的分层体系。
