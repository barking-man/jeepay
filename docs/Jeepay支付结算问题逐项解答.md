# 第一部分：交易系统生产问题

## 问题 1：为什么订单先落库再调用渠道？

【Jeepay 现状】

Jeepay 生成支付单后，先以 `INIT` 状态保存，再调用渠道。

先落库的原因：

1. 固定平台支付单号；
2. 渠道请求使用平台订单号作为幂等键；
3. 渠道回调到达时能找到本地订单；
4. 渠道请求超时后仍能按原单号查询；
5. 后续退款、通知、分账和对账都有稳定主键。

如果先调用渠道、后落库，可能出现：

```text
渠道订单已经创建
→ 本地写库失败
→ 本地不知道渠道单号
→ 回调无法关联
→ 用户可能已经付款但系统没有本地交易
```

【背诵结论】

> 支付中心必须先创建本地交易凭证，再发起不可回滚的外部渠道调用。数据库和渠道无法组成一个事务，只能通过稳定订单号、状态机、查单、补偿和对账保持一致。

## 问题 2：渠道超时、未知、系统异常分别怎么处理？

### 渠道超时

含义：

```text
请求可能没有到达渠道
也可能渠道已经创建订单或扣款，但响应丢失
```

处理：

```text
订单进入 ING
→ 按原平台订单号主动查询渠道
→ 明确成功则补成功
→ 明确失败则补失败
→ 仍未知则继续补偿
```

不能直接判失败并重新下单。

### 渠道结果未知

`UNKNOWN` 表示当前无法确认，不是失败。

处理：

- 保持 `ING`；
- 延迟 MQ 查单；
- 定时任务继续查询；
- 保存渠道错误信息；
- 超过阈值进入告警或人工差错。

### 渠道接口异常

`API_RET_ERROR` 表示接口返回异常状态，结果不可靠。

Jeepay 当前把它映射到 `ING`。

后续必须查原渠道。

### 支付中心自身异常

`SYS_ERROR` 表示 Jeepay 自身无法完成处理。

【Jeepay 现状】

- 通常不改变支付状态，订单可能停留在 `INIT`；
- 普通支付定时补单只扫描 `ING`，不扫描 `INIT`；
- 两小时后过期任务可能直接关闭订单；
- 没有完整的未决异常队列。

【生产补全】

- 记录异常发生在渠道调用前还是调用后；
- 保存渠道请求 ID 和报文证据；
- 已调用渠道但结果未知的订单显式标记 `UNKNOWN`；
- 自动查询原渠道；
- 超过阈值才进入人工处理。

## 问题 3：如何保证重复下单、重复回调不产生重复交易？

### 重复下单

Jeepay 支付单唯一键：

```text
mch_no + mch_order_no
```

同一商户无法创建相同商户订单号的第二笔支付单。

当前完成后再次提交通常会返回“商户订单已存在”。

【生产补全】

保存首次请求摘要和响应，实现完整幂等：

- 相同订单号、相同请求内容：返回原订单和原结果；
- 相同订单号、不同金额或内容：返回幂等冲突。

### 重复回调

支付状态使用条件更新：

```text
UPDATE ...
SET state = SUCCESS
WHERE pay_order_id = ?
AND state = ING
```

第二条重复成功回调更新不到行，因此不能重复推进状态。

其他防线：

- 通知记录唯一键 `order_id + order_type`；
- 分账父状态条件更新；
- 分账记录状态条件更新；
- 账务事件唯一键；
- 结算明细唯一占用。

【背诵结论】

> 防重复下单靠商户订单号唯一约束，防重复回调靠状态 CAS 和业务唯一键。不能只靠先查询再写入。

## 问题 4：条件更新、唯一索引、行锁、乐观锁分别用在哪里？

### 条件更新

适合订单状态机：

```text
INIT → ING
ING → SUCCESS/FAIL/CLOSED
```

只有旧状态满足条件才允许迁移。

Jeepay 的支付、退款、转账状态更新都采用这个思路。

### 唯一索引

适合防止业务记录重复：

- 支付单：`mch_no + mch_order_no`；
- 退款单：`mch_no + mch_refund_no`；
- 转账单：`mch_no + mch_order_no`；
- 通知：`order_id + order_type`；
- 账务事件幂等键；
- 结算明细唯一占用。

### 行锁

适合必须串行计算的资金操作：

- 支付单锁；
- 商户账户余额锁；
- 退款额度预占；
- 结算单生成；
- 出款前余额冻结。

### 乐观锁

适合状态或配置的低冲突更新：

```text
version = N
UPDATE ... SET version=N+1 WHERE version=N
```

冲突后必须重新读取并判断业务事实，不能只盲目重试。

【背诵结论】

> 唯一索引防止产生重复记录，条件更新控制状态迁移，行锁保护强一致金额计算，乐观锁适合低冲突状态更新。

## 问题 5：数据库提交成功但 MQ 没发出怎么办？

问题场景：

```text
支付订单已经提交成功
→ 服务在发送 MQ 前崩溃
→ 通知或分账消息没有发出
→ MQ 不知道这条业务事件
```

如果先发 MQ、数据库失败，也可能出现相反问题。

【生产补全：Outbox】

1. 支付状态更新和 outbox 事件在同一数据库事务提交；
2. 独立发布器扫描未发送事件；
3. 发布到 MQ；
4. 记录发布时间；
5. 消费方按事件 ID 幂等；
6. 定时扫描长期未发布事件。

【Jeepay 现状】

- 支付成功后再创建通知和分账消息；
- 没有统一 Outbox；
- 服务在状态更新和消息发送之间崩溃时，依赖扫描和人工发现。

【背诵结论】

> 数据库和 MQ 不能用普通本地事务一起提交，应该使用 Outbox 保存待发事件，再由发布器可靠投递。

## 问题 6：MQ 重复消费、延迟、丢失分别怎么兜底？

### 重复消费

- 重新读取数据库当前状态；
- 不信消息中的旧状态；
- 使用状态 CAS；
- 使用通知、账务、结算唯一键；
- 重复消息直接幂等返回。

### 延迟

- 接受延迟是正常现象；
- 监控消息年龄和积压；
- 对资金终态使用定时扫描兜底；
- 关键通知增加巡检任务。

### 丢失

- 依赖数据库状态扫描；
- Outbox 定期重发；
- 分账、通知、查单分别设置补偿任务；
- 死信队列；
- 人工重放工具。

【Jeepay 现状】

- 支付有延迟 MQ 查单；
- 通知依靠延迟 MQ 重试；
- 自动分账依靠延迟 MQ；
- 状态更新和消息发送没有事务 Outbox；
- 没有独立的长期通知巡检任务。

## 问题 7：支付成功但本地更新失败怎么恢复？

场景：

```text
渠道已经明确支付成功
→ 本地数据库事务失败
→ 本地仍为 INIT 或 ING
```

处理：

1. 保存渠道回调或查询证据；
2. 按原平台订单号重新查询渠道；
3. 核对金额、币种和商户；
4. 在本地执行合法状态修复；
5. 补商户通知；
6. 补自动分账；
7. 补账务事件；
8. 记录异常修复审计。

不能：

- 重新创建支付单；
- 重新调用渠道下单；
- 只改支付状态而不补通知和账务。

---

## 问题 8：本地已关闭但渠道成功如何处理？

这是“晚到成功”。

处理：

1. 验签；
2. 查询渠道确认真实成功；
3. 保存渠道订单和回调证据；
4. 记录晚到支付异常；
5. 判断商户业务是否已经履约；
6. 已履约：补支付事实，不重复发货；
7. 未履约但允许履约：补支付事实并通知商户履约；
8. 不允许履约或库存不足：补支付事实后发起退款；
9. 不确定：人工处理；
10. 日终再次对账。

【Jeepay 现状】

普通支付回调主要处理 `ING`，没有完整的 `CLOSED → SUCCESS` 异常修复流程。

## 问题 9：如何设计幂等重试、退避、熔断和渠道隔离？

### 幂等重试

- 支付使用原平台订单号；
- 退款使用原退款单号；
- 转账使用原转账单号；
- 每次重试不得更换业务键；
- 数据库唯一约束作为最后防线。

### 退避

- 指数退避；
- 随机抖动；
- 最大次数；
- 最大等待时间；
- 持久化下次查询时间。

### 熔断

- 按渠道统计错误率和超时率；
- 渠道故障时停止新建调用；
- 已未知订单仍继续查原渠道；
- 半开状态少量探测恢复。

### 渠道隔离

- 独立连接池；
- 独立线程池；
- 独立超时；
- 独立限流；
- 下游慢请求不能占满全部支付线程。

【Jeepay 现状】

- 没有完整熔断器；
- MQ 多个业务共用线程池；
- 渠道调用隔离能力有限。

## 问题 10：多实例定时任务如何防止重复扫描？

【Jeepay 现状】

支付补单、退款补单、转账补单、分账补单和过期任务都使用 Spring 定时任务，代码中没有明确分布式锁。

多实例部署时可能同时扫描同一批记录。

【生产方案】

- 分布式任务调度；
- leader election；
- 数据库行级领取；
- 按 ID 区间分片；
- 乐观锁抢占；
- 每项业务幂等；
- 记录任务水位。

即使任务重复执行，也必须保证：

- 查询幂等；
- 状态 CAS；
- 通知唯一；
- 分账唯一；
- 账务唯一。

## 问题 11：热点商户、热点账户、深分页和大表扫描怎么优化？

### 热点商户

- 按商户限流；
- 大商户独立配额；
- 缓存配置；
- 数据按商户分片。

### 热点账户

- 不直接高频更新单行余额；
- 先写不可变明细；
- 按账户或日期分桶；
- 结算时汇总；
- 日终重算校验。

### 深分页

避免：

```text
LIMIT 1000000, 100
```

采用：

- 游标分页；
- 主键范围查询；
- 时间窗口；
- 小批次流式处理。

### 大表扫描

- 按创建时间或商户分区；
- 为状态扫描建联合索引；
- 归档历史订单；
- 对账走独立数据源；
- 不再用全表统计支撑实时页面。

【Jeepay 现状】

- 支付和转账表只有有限的业务索引；
- 退款、分账、通知巡检所需联合索引不足；
- 定时任务使用页码分页，处理过程中结果集缩小时可能跳过部分记录。

# 第二部分：商户、渠道、账务和合规问题

## 问题 12：普通商户、服务商商户和应用分别是什么？

- 服务商 `isv_no`：渠道合作和服务商模式的管理主体；
- 商户 `mch_no`：交易收款、退款、分账和对账的业务主体；
- 应用 `app_id`：API 调用和签名主体。

普通商户自己配置渠道参数。

特约商户挂在服务商下，需要服务商参数加子商户参数。

一个商户可以有多个应用。

订单同时保存 `mch_no + isv_no + app_id`，避免依赖当前配置解释历史订单。

## 问题 13：商户费率和上游渠道成本有什么区别？

`t_mch_pay_passage.rate`：

```text
Jeepay 向商户计算手续费使用的费率
```

支付单保存为 `mch_fee_rate`。

`t_pay_interface_config.if_rate`：

```text
支付接口配置中的渠道或接口费率
```

当前支付单手续费使用商户通道路由中的 `rate`，不是自动使用 `if_rate`。

例如：

```text
商户费率 0.60%
支付宝成本 0.38%
```

用户支付 100 元：

```text
商户手续费 = 0.60
支付宝成本 = 0.38
差额 = 0.22
```

Jeepay 当前只记录交易手续费，不自动完成 0.22 元的价差扣收和账务。

## 问题 14：多通道路由、限额、成本和故障转移怎么设计？

路由前应考虑：

- 商户产品开通；
- 渠道状态；
- 支付方式；
- 单笔和日累计限额；
- 渠道成本；
- 成功率；
- 渠道并发；
- 风控标签；
- 结算周期。

但必须遵守：

> 只有渠道调用前可以选路。已经调用渠道且状态未知后，只能查原渠道，不能换路由重新下单。

【Jeepay 现状】

- 有商户应用、支付方式、渠道和费率路由；
- 没有成熟的权重、成本优先和成功率故障转移算法。

## 问题 15：渠道维护、参数错误、证书过期怎么处理？

- 渠道维护：停止新交易，监控恢复；
- 参数错误：拒绝新交易并告警；
- 证书临期：提前轮换；
- 证书过期：该渠道熔断，禁止新下单；
- 已使用该渠道的未知订单：仍按原渠道查单；
- 配置更新：保存版本、灰度和审计；
- 回滚不能影响历史订单快照。

---

## 问题 16：商户停用、应用停用和密钥重置后如何快速生效？

Jeepay：

- 下单时校验商户和应用状态；
- 商户应用和服务商配置使用本地内存缓存；
- 配置刷新依赖 MQ；
- 关闭缓存开关时直接查询数据库。

【生产补全】

- 缓存设置 TTL；
- 配置版本号；
- MQ 广播刷新；
- 定时全量校准；
- 密钥新旧版本并行；
- 停用操作立即失效相关 token；
- 多实例一致性监控。

---

## 问题 17：支付订单为什么不能代替账务分录？

支付订单只回答交易是否成功，不能完整表达：

- 渠道应收；
- 商户应付；
- 手续费收入；
- 渠道成本；
- 退款负债；
- 冻结与可结算余额；
- 平台垫资。

账务要满足：

```text
借贷平衡
事件幂等
历史不可改
余额可由分录重算
```

【Jeepay 现状】

没有复式记账表，支付订单不是会计分录。

---

## 问题 18：支付、退款、分账和结算如何记账？

支付成功示例：

```text
借：渠道清算应收     100.00
    贷：商户待结算     99.40
    贷：手续费收入      0.60
```

渠道到账：

```text
借：银行存款           99.62
借：渠道成本            0.38
    贷：渠道清算应收    100.00
```

结算：

```text
借：商户待结算         99.40
    贷：银行存款        99.40
```

退款使用相反方向的新分录，不修改原支付分录。

# 第三部分：末尾 15 个核心问题

## 核心问题 1：支付成功、通知成功、记账成功、结算成功有什么区别？

- 支付成功：渠道明确确认用户扣款或授权；
- 通知成功：商户收到结果并返回约定成功响应；
- 记账成功：支付、退款等事实生成唯一账务事件和会计分录；
- 结算成功：商户可结算资金已完成出款并确认到账。

四者可能在不同时间完成。

Jeepay 实现支付、通知和部分分账；没有账务和结算。

---

## 核心问题 2：回调为什么不能直接修改订单，而要做状态条件更新？

回调可能重复、乱序、早到和并发。

正确更新：

```text
UPDATE pay_order
SET state = SUCCESS
WHERE pay_order_id = ?
AND state = ING
```

更新行数为 0 时，说明状态已被其他事件推进，不能重复通知、分账或记账。

Jeepay 支付回调主要处理 `ING`，项目对早到 `INIT` 和晚到 `CLOSED` 的异常处理仍不完整。

---

## 核心问题 3：渠道查询和商户查询有什么区别？

商户查询：

- Jeepay 的 `/api/pay/query`、退款查询、转账查询；
- 主要读取 Jeepay 本地数据库；
- 返回 Jeepay 当前记录。

渠道查询：

- Jeepay 内部调用微信、支付宝等；
- 获取支付机构真实状态；
- 用于补单、超时恢复和回调缺失。

---

## 核心问题 4：退款为什么要独立订单？

- 一笔支付可以多次部分退款；
- 每次退款有自己的渠道订单号；
- 每次退款有独立状态、失败原因和通知；
- 支付单需要原子累计退款金额。

Jeepay：

```text
t_refund_order.refund_amount  本次退款
t_pay_order.refund_amount     累计成功退款
```

退款成功才会更新支付单累计金额。

---

## 核心问题 5：并发退款如何保证不超退？

【Jeepay 当前防线】

- 检查已有 `ING` 退款；
- 检查累计退款金额；
- 退款成功回写支付单时再次检查累计金额不超过支付金额。

【仍存在的风险】

两个退款请求可以同时通过“是否存在 processing refund”的查询。

【生产补全】

- 支付单行锁；
- 退款额度冻结；
- 唯一额度占用；
- 调用渠道前原子预占；
- 成功转已退款，失败释放，未知保持冻结。

---

## 核心问题 6：转账超时为什么不能直接重发？

转账是实际出款。

超时可能是：

- 渠道没收到；
- 渠道处理失败；
- 渠道已经成功但响应丢失。

直接重发可能重复出款。

正确处理：

```text
保持 ING
→ 按原平台转账单号查渠道
→ 明确成功或失败后再处理
```

Jeepay 的转账补单只扫描最近一天内创建的 `ING` 转账；超过一天仍未知需要人工处理。

---

## 核心问题 7：分账和结算有什么区别？

分账决定交易收入归谁：

```text
商户、平台、服务商、门店、供应商分别多少
```

结算决定可结算资金何时出款：

```text
账期、对账、冻结、余额、结算单、出款、到账
```

Jeepay 有分账，没有完整结算。

---

## 核心问题 8：分账父状态结束为什么不代表全部成功？

`division_state=3` 只表示本轮任务结束。

每个接收方有自己的记录状态：

```text
WAIT
SUCCESS
FAIL
ACCEPT
```

同一轮可以部分成功、部分失败、部分已受理。

结算只能使用明确成功的分账记录。

---

## 核心问题 9：支付订单如何进入复式记账？

```text
支付成功
→ 唯一账务事件
→ 会计凭证
→ 借贷分录
→ 账户余额
```

重复回调依靠账务事件唯一键防重复。

退款和分账分别生成独立账务事件。

【Jeepay 现状】

没有账务事件、凭证、分录和余额表。

---

## 核心问题 10：对账发现差异后为什么不能直接修订单？

差异可能是：

- 文件延迟；
- 订单号映射错误；
- 重复账单；
- 金额或手续费错误；
- 本地漏单；
- 渠道退单；
- 跨日交易。

直接改订单会绕过通知、账务、分账和结算。

正确流程：

```text
校验账单
→ 匹配
→ 分类
→ 查渠道证据
→ 自动修复或人工审核
→ 修复业务状态
→ 补账务调整
→ 复核余额
→ 关闭差错工单
```

---

## 核心问题 11：结算后的退款从哪里扣钱？

结算前退款：

```text
扣商户待结算金额
```

结算后退款：

```text
扣商户可结算余额
→ 不足则下期抵扣
→ 冻结后续结算
→ 形成商户欠款
→ 必要时使用风险准备金
```

Jeepay 当前没有商户余额和结算后退款追偿。

---

## 核心问题 12：如何防止同一交易重复进入结算？

- 账务事件唯一；
- 结算明细唯一占用；
- 同一事件只能进入一个有效批次；
- 固定业务日和输入水位；
- 重复任务采用幂等批次；
- 出款单唯一；
- 审批后的历史结算不覆盖。

---

## 核心问题 13：出款成功后退票怎么处理？

```text
出款单 SUCCESS
→ 银行退票
→ 出款单改为 RETURNED
→ 冲回银行存款
→ 恢复商户应付或形成商户欠款
→ 确认旧出款不可能再次成功
→ 再决定是否重新出款
```

---

## 核心问题 14：MQ 为什么不能保证只消费一次？

MQ 通常是至少一次投递：

- ACK 可能丢失；
- 消费者可能重启；
- 网络可能抖动；
- 生产者可能重复发送；
- 多实例可能竞争。

所以支付状态要 CAS，通知要唯一，账务事件要唯一，结算要唯一占用。

---

## 核心问题 15：晚到支付、重复回调和本地状态冲突怎么处理？

步骤：

1. 验签并校验订单、金额、币种和商户；
2. 主动查渠道确认；
3. 保存回调证据；
4. 根据本地状态分支。

本地 `ING`：

```text
→ SUCCESS 或 FAIL
```

本地 `SUCCESS`：

```text
→ 幂等确认，不重复通知和分账
```

本地 `CLOSED`：

```text
→ 晚到支付
→ 查渠道和商户履约
→ 补履约或退款
→ 进入差错和账务调整
```

Jeepay 当前没有完整的晚到支付补偿流程，需要生产化扩展。

---

# 极简背诵版

1. 先落库是为了固定订单号，支持幂等、回调和超时查询。
2. 超时和未知不是失败，必须查原渠道；自身异常可能留在 `INIT`。
3. 防重复下单靠商户订单号唯一，防重复回调靠状态 CAS。
4. 唯一索引防重，CAS 管状态，行锁保强一致，乐观锁处理低冲突并发。
5. 数据库和 MQ 之间需要 Outbox。
6. MQ 重复靠幂等，延迟靠监控，丢失靠状态扫描。
7. 渠道成功本地失败必须查询渠道并补状态、通知和账务。
8. 本地关闭渠道成功属于晚到支付，必须查履约后补单或退款。
9. 重试必须使用原业务单号，配合退避、熔断和渠道隔离。
10. 多实例任务必须有分布式调度或幂等领取。
11. 热点和深分页通过限流、分片、游标和归档解决。
12. 支付成功、通知成功、记账成功、结算成功是四个不同事实。
13. 退款必须独立，累计金额成功后才更新。
14. 转账超时只能查原单，不能重复出款。
15. 分账不等于结算，父任务结束不等于全部成功。
16. 支付订单不能代替复式记账。
17. 对账差异不能直接覆盖订单。
18. 结算后退款从商户余额、下期结算或欠款扣回。
19. 出款成功还要核对银行回单和退票。
20. Jeepay 是交易底座，不是完整账务、对账和清结算系统。
