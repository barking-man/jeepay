# Jeepay 支付与结算求职实战计划

## 1. 计划目标

本计划面向以下情况：

- 具备 Java、Spring Boot、MySQL 等后端基础。
- 没有真实支付、账务、对账和结算工作经验。
- 希望通过 Jeepay 源码学习和二次开发，形成能够被演示、验证和深入追问的项目经验。
- 目标岗位为 Java 后端、支付研发、交易研发、账务研发或清结算研发。

计划周期为 8 周，建议每周投入 12 至 15 小时。完成后应达到以下目标：

1. 能完整讲解一笔支付从商户请求到渠道支付、异步回调和商户通知的链路。
2. 能解释支付、退款、转账、分账、清分、清算、对账和结算的区别。
3. 能分析重复请求、回调丢失、渠道超时、状态乱序和 MQ 重复消费等问题。
4. 能独立实现一个模拟支付通道、一个最小对账模块和一个最小账务结算模块。
5. 能用代码、测试报告、流程图和故障演练记录证明自己的项目实践。

计划范围明确排除以下内容：

- 不学习 Docker、Linux 服务器、Shell 一键安装、Nginx、HTTPS 等部署运维内容。
- 环境仅限本机 Windows，用 IntelliJ IDEA 启动、断点调试和验证。
- 涉及部署的文档只阅读与本地启动相关的部分，其余跳过。

## 2. 经历表述边界

本计划的目标是获得真实、可验证的项目实践，不是伪造任职经历或生产数据。

可以表述：

> 基于 Jeepay 聚合支付系统完成二次开发，跟踪并改造支付、退款、异步回调和商户通知链路；实现模拟支付通道、渠道账单对账、差错处理、复式记账及 T+1 商户结算模块；通过重复回调、MQ 重复消费、渠道超时和跨日退款等故障演练验证系统幂等性与最终一致性。

不应表述：

- 虚构在某家公司负责支付系统。
- 虚构生产交易量、资金规模、线上事故或客户数量。
- 将本地压测结果描述成真实生产指标。
- 将自己没有参与过的第三方项目成果写成个人成果。

被问到生产经验时，可以直接回答：

> 我没有真实生产资金处理经历，但独立完成了接近生产业务规则的支付结算项目，并对关键异常进行了故障模拟、补偿设计和测试验证。

## 3. 项目能力边界

Jeepay 当前开源代码适合学习以下内容：

- 普通商户与服务商模式。
- 商户、应用、支付方式、支付接口和支付通道路由。
- 统一下单、查单、关单和异步回调。
- 退款、转账和分账。
- 商户通知、MQ、定时补单和订单过期处理。
- 微信、支付宝等渠道适配层设计。

以下内容在当前仓库中并不完整，需要作为二次开发项目补充：

- 会计账户和复式记账。
- 渠道账单下载与标准化。
- 支付系统、业务系统、支付渠道之间的对账。
- 差错处理和人工审核。
- 日切、结算周期、结算批次和商户出款。
- 结算后的退款追偿和负余额处理。

需要始终区分：

| 概念 | 含义 |
|---|---|
| 支付 | 用户通过支付渠道向商户完成付款 |
| 退款 | 将已支付资金全部或部分退回用户 |
| 转账 | 平台主动向指定账户划转资金 |
| 分账 | 按规则将一笔交易金额分配给多个接收方 |
| 清分 | 根据交易、费率和参与方计算各方应收应付 |
| 清算 | 汇总参与方债权债务，形成净额或清算结果 |
| 对账 | 比较不同系统的交易记录，识别不一致 |
| 结算 | 根据结算结果实际执行资金划拨或出款 |
| 账务 | 用账户和流水持续记录资金权益变化 |

分账不等于结算，支付订单也不能代替账务流水。

## 5. 学习方法

每学习一条业务链路，都回答以下问题：

1. 谁是调用方，谁是服务方？
2. 商户订单号、平台订单号、渠道订单号分别在哪里生成？
3. 使用什么字段或唯一索引防止重复下单？
4. 订单状态允许怎样转换，哪些转换禁止发生？
5. 金额使用什么单位和类型，费率如何计算？
6. 本地事务边界在哪里？
7. 调用渠道超时时，为什么不能直接判定失败？
8. 同步响应、异步回调和主动查单发生冲突时相信谁？
9. 重复回调和 MQ 重复消息如何保证幂等？
10. 系统最终依靠什么机制发现并修复数据差异？

每天建议采用以下节奏：

- 30 分钟：支付业务概念。
- 60 分钟：源码阅读和断点调试。
- 30 分钟：画图、写测试或整理问题。

每周必须留下至少一种可检查成果，禁止只看视频和阅读文章。

## 6. 第 0 阶段：准备环境

建议用 1 至 2 天完成。

### 环境边界

本计划只在你的本机 Windows 上运行与调试，使用 IntelliJ IDEA。不涉及 Docker、Linux、Shell 安装脚本、Nginx、HTTPS 等部署运维内容，`docs/deploy/` 下与本地启动无关的文档跳过。

### 6.1 安装本机中间件

- JDK 17 和 Maven 3.8+。
- MySQL 8.0：本机安装并启动，创建数据库 `jeepay`（utf8mb4），执行 `docs/sql/init.sql`（当前版本全量建表和初始化数据；`docs/sql/patch.sql` 是旧版本升级用的增量脚本，全新安装不需要执行）。
- Redis：本机 6379 端口。Windows 下可用 Memurai 或 redis-windows 社区构建，也可以使用你已有的现成环境。
- MQ：推荐 ActiveMQ，Windows 原生支持最好。项目默认使用 RocketMQ，但 ActiveMQ 依赖已经打包进 `jeepay-components/jeepay-components-mq`，只需改配置；如果你本机已经装好 RocketMQ，也可以直接用默认配置。
- API 调试工具（如 Apifox/Postman）和数据库客户端（如 Navicat/DBeaver）。

### 6.2 配置说明：只需改一处

`conf/devCommons/config/application.yml` 是开发通用配置，各模块的 pom 会把它打进 classpath，开发期只改这一份即可。默认值：

- MySQL：`127.0.0.1:3306/jeepay`，用户名 `root`、密码 `123`。
- Redis：`127.0.0.1:6379`；库位约定：运营平台 1 库、商户系统 2 库、支付网关 3 库（已在各模块 `application.yml` 配好，了解即可）。
- MQ：`isys.mq.vender: rocketMQ`，name-server `127.0.0.1:9876`。

如果改用 ActiveMQ：

- 把 `isys.mq.vender` 改为 `activeMQ`。
- 启用 `spring.activemq` 段（broker-url 为 `tcp://127.0.0.1:61616`），并注释掉根级的 `rocketmq:` 段。
- 先启动 ActiveMQ，再启动应用。

### 6.3 启动顺序

1. 在仓库根目录执行 `mvn clean install`，先编译全部模块，确保 `conf/devCommons` 被复制进 classpath。
2. 用 IDEA 打开仓库根目录，等待 Maven 依赖导入完成。
3. 依次启动三个后端服务：`jeepay-payment`（9216）、`jeepay-manager`（9217）、`jeepay-merchant`（9218）。
4. 创建本地学习分支，例如 `learning/payment-settlement`。
5. 为学习笔记、流程图、测试数据和接口用例建立独立目录；不接入真实资金账户，优先使用沙箱或后续开发的 Mock 通道。

### 6.4 本地启动常见问题

- 报数据库认证错误：确认本机 MySQL 密码与 `conf/devCommons` 中的配置一致（默认 `root/123`），url 已带 `allowPublicKeyRetrieval=true&useSSL=false`，一般无需再改。
- 日志报 MQ 连接失败：确认 `isys.mq.vender` 与实际启动的 MQ 一致，先启动 MQ 再启动应用。
- 端口占用：9216/9217/9218 被占用时，修改对应模块 `application.yml` 中的 `server.port`。
- `cache-config: true` 依赖 MQ 广播模式同步配置缓存，若改配置后不生效，检查 MQ 广播消费是否正常，或临时改为 `false` 直查数据库。

### 验收

- 服务能够启动。
- 能登录运营平台和商户平台。
- 能找到支付订单、退款订单、商户、应用和支付通道配置。
- 能说明各个后端模块使用的端口和职责。

## 12. 第 6 周：渠道对账模块

### 学习目标

- 理解对账是发现最终不一致的核心兜底机制。
- 能实现账单标准化、批次管理、差错分类和处理闭环。

### 最小功能范围

1. 导入 Mock 渠道 CSV 账单。
2. 将不同渠道账单转换为统一账单记录。
3. 按渠道订单号匹配本地支付订单。
4. 比较订单状态、支付金额、手续费和退款金额。
5. 生成对账批次、平账记录和差错记录。
6. 支持人工确认、忽略、补单和挂账等处理状态。
7. 保存操作人、处理时间、处理前后数据和备注。
8. 同一渠道、账单日期和账单文件不能重复执行。

### 必须识别的差错

- 本地成功，渠道无记录。
- 本地失败或处理中，渠道成功。
- 本地无记录，渠道存在交易。
- 本地金额与渠道金额不一致。
- 渠道账单重复。
- 退款状态或退款金额不一致。
- 手续费不一致。

### 处理原则

- 对账程序负责发现差异，不应无条件自动修改订单。
- 自动补单必须验证渠道订单号、商户、金额和原始请求。
- 涉及资金的人工处理必须留下审核和审计记录。
- 原始渠道账单应保留，标准化数据不能覆盖原始数据。
- 对账任务必须支持失败重跑且结果幂等。

### 本周产出

- 对账数据库设计。
- 渠道账单解析接口和 Mock CSV 实现。
- 对账批次服务和差错查询接口。
- 至少 7 类差错测试数据。
- 一份对账结果报告。

### 验收

- 同一账单重复导入不会生成重复批次。
- 平账数量和差错数量可复核。
- 每条差错能追溯本地订单和渠道原始记录。
- 差错处理过程有完整审计日志。

## 13. 第 7 周：账务与商户结算模块

### 学习目标

- 理解支付订单系统与账务系统的职责边界。
- 理解复式记账、余额、日切、结算周期和结算批次。
- 建立一个可验证但不连接真实资金的 T+1 结算原型。

### 账户模型

至少区分：

- 渠道清算或应收账户。
- 商户待结算账户。
- 商户可结算账户。
- 平台手续费收入账户。
- 退款或调账账户。

余额至少区分：

- 可用金额。
- 待结算金额。
- 冻结金额。

实际账户方向和会计科目必须基于项目设定的资金模式统一设计，不能在不同业务中随意改变。

### 结算规则

- 设置明确的日切时间和结算日期。
- 第一版实现 T+1，避免同时处理多个账期。
- 只选择支付成功、已对账、未结算且满足账期的交易。
- 退款、手续费、分账和调账必须有明确归属周期。
- 使用唯一约束防止一笔交易进入多个有效结算单。
- 结算金额不能小于最小结算金额。
- 负结算金额进入下期抵扣或人工处理，不直接出款。
- 结算失败可以重试，但不能生成重复转账。

示例关系：

```text
结算金额
= 交易金额
- 退款金额
- 商户手续费
- 应扣分账金额
+ 调账金额
```

该公式只是项目原型的业务约定。真实系统需要根据渠道手续费承担方、分账模式、退款手续费政策和资金存管模式调整。

### 实践任务

- 支付成功时生成唯一记账事件。
- 对同一支付成功事件重复消费，验证不会重复记账。
- 执行日切，将符合条件的待结算金额转为可结算金额。
- 生成商户 T+1 结算批次和结算明细。
- 使用 Mock 转账执行结算出款。
- 模拟出款请求超时，通过主动查询确认最终状态。
- 设计结算后退款在下一期扣回的处理方式。

### 本周产出

- 账户和账务流水 ER 图。
- 支付、退款、手续费和结算记账规则。
- T+1 结算代码。
- 结算批次、结算单和结算明细接口。
- 借贷平衡和余额一致性测试。

### 验收

- 同一业务事件重复处理不会重复入账。
- 每张记账凭证借贷平衡。
- 账户余额能够由账务流水重新计算和验证。
- 同一支付订单不能重复参与有效结算。
- 结算出款超时不会直接标记为失败并再次出款。
