# Jeepay 支付结算核心问题完整解答

## 文档说明

本文基于当前工作区的 Jeepay 代码、数据库和定时任务逐题回答支付结算岗位的核心问题。

标记说明：

- `【Jeepay 现状】`：当前项目代码真实具备的能力；
- `【异常与兜底】`：线上异常时的处理原则；
- `【生产补全】`：Jeepay 当前没有完整实现，但生产系统必须具备的能力；
- `【背诵结论】`：适合直接口述和记忆的结论。

# 问题一：支付成功、通知成功、记账成功、结算成功有什么区别？

## 1. 支付成功

支付成功是渠道明确确认用户已经完成扣款或授权。

对 Jeepay 来说，支付单从：

```text
ING → SUCCESS
```

但支付成功只代表交易事实，不代表商户业务已经履约。

## 2. 通知成功

通知成功是 Jeepay 把支付结果发送给商户，并且商户返回约定的成功响应。

在 Jeepay 中：

- 支付成功首先创建 `t_mch_notify_record`；
- 记录状态为 `1 通知中`；
- 商户返回 `SUCCESS` 后改为 `2 通知成功`；
- 达到重试上限仍失败则改为 `3 通知失败`。

通知失败不能回滚支付成功。

## 3. 记账成功

记账成功是把支付事实转换为账务事件和会计分录。

例如用户支付 100 元，商户手续费 0.60 元，概念上的分录是：

```text
借：渠道清算应收       100.00
    贷：商户待结算      99.40
    贷：手续费收入       0.60
```

【Jeepay 现状】

Jeepay 只有交易订单和手续费字段，没有完整复式记账表、会计凭证和余额账户，因此当前订单成功不等于已经生成会计分录。

## 4. 结算成功

结算成功表示：

- 交易已完成对账；
- 账务事实已确认；
- 商户资金已经满足结算条件；
- 已生成结算单；
- 已执行出款；
- 银行或渠道已经确认到账。

【Jeepay 现状】

Jeepay 没有商户余额、结算批次、结算单和结算出款模块。

## 四者关系

```text
支付成功
→ 商户通知可能成功或失败
→ 账务可能尚未记账
→ 交易仍需渠道对账
→ 账期满足后才可结算
→ 出款后还要确认银行回单
```

【背诵结论】

> 支付成功是资金交易事实，通知成功是消息送达事实，记账成功是债权债务入账事实，结算成功是商户资金实际释放事实。四者不能互相替代。

# 问题二：回调为什么不能直接修改订单，而要做状态条件更新？

## 1. 回调不是只来一次

渠道可能：

- 重复发送同一成功回调；
- 重复发送同一失败回调；
- 先发送失败，后发送成功；
- 先发送成功，后发送处理中；
- 在本地尚未完成状态更新时提前回调；
- 在本地关单后才发送成功回调；
- 多个实例同时处理同一条回调。

如果代码直接执行：

```text
payOrder.setState(SUCCESS)
updateById(payOrder)
```

后到达的旧消息可能覆盖新状态，或者重复触发通知和分账。

## 2. 条件更新相当于数据库 CAS

Jeepay 的支付状态更新带有原状态条件：

```text
UPDATE t_pay_order
SET state = SUCCESS
WHERE pay_order_id = ?
AND state = ING
```

只有当前仍为 `ING` 的请求才能把订单推进到成功。

重复成功回调再次执行时更新行数为 0，说明状态已经被其他请求推进，当前请求不应重复执行业务副作用。

失败、关闭也使用同样的思路。

## 3. Jeepay 当前回调逻辑

支付异步回调主体主要处理 `ING`：

```text
ING + 渠道明确成功 → SUCCESS
ING + 渠道明确失败 → FAIL
```

回调验签后还要校验：

- 平台订单号；
- 渠道订单号；
- 渠道商户或应用；
- 金额；
- 币种；
- 渠道交易状态。

## 4. 早到回调

如果回调到达时本地还是 `INIT`，普通 `ING → SUCCESS` 的条件更新不会成功。

【Jeepay 现状】

当前支付回调只明确处理 `ING`，对早到回调存在状态竞争风险。

【生产补全】

- 保存回调原始证据；
- 对早到回调做延迟处理；
- 主动查询渠道；
- 必要时支持受控的 `INIT → SUCCESS/FAIL`；
- 不允许简单丢弃回调。

## 5. 重复回调的完整防线

- 支付状态条件更新；
- 通知记录唯一键 `order_id + order_type`；
- 分账父状态条件更新；
- 分账记录状态条件更新；
- 账务事件唯一幂等键；
- 结算明细唯一占用。

【背诵结论】

> 回调可能重复、乱序、早到和并发，不能按消息到达顺序覆盖状态。支付订单必须通过带旧状态条件的 CAS 收敛，重复回调只能幂等确认，不能重复通知、分账、记账或结算。

# 问题三：渠道查询和商户查询有什么区别？

## 1. 商户查询

商户调用 Jeepay：

```text
/api/pay/query
/api/refund/query
/api/transfer/query
```

【Jeepay 现状】

这些接口主要按商户身份查询 Jeepay 本地数据库中的支付、退款和转账记录。

特点：

- 查询本地当前状态；
- 不保证每次实时调用渠道；
- 适合商户确认 Jeepay 当前结果；
- 响应会带平台订单号和当前状态。

## 2. 渠道查询

Jeepay 内部使用渠道查询适配器：

- 支付查询；
- 退款查询；
- 转账查询；
- 分账查询。

渠道查询使用平台订单号、退款单号或渠道批次号，向微信、支付宝、银联等机构获取真实交易状态。

## 3. 使用场景

| 场景 | 使用查询 |
|---|---|
| 商户页面展示当前订单 | Jeepay 本地查询 |
| 回调丢失 | Jeepay 渠道查询 |
| 下单接口超时 | Jeepay 渠道查询 |
| 退款状态长时间不变 | Jeepay 渠道退款查询 |
| 转账状态未知 | Jeepay 渠道转账查询 |
| 对账差异 | 渠道账单和本地记录 |

## 4. 当前风险

如果本地订单错误地停在未决状态，商户查询只能看到这个错误状态，不能自行修复。

因此 Jeepay 必须有内部补单任务。

【背诵结论】

> 商户查询回答“Jeepay 现在记成了什么”，渠道查询回答“支付机构最终认定是什么”。两者不能混为一谈。

# 问题四：退款为什么要独立订单？

## 1. 一笔支付可以对应多次退款

例如原支付：

```text
100 元
```

可以发生：

```text
退款20元
退款30元
退款50元
```

如果直接修改支付订单，无法保留每次退款的独立事实。

## 2. Jeepay 退款表和状态

每笔退款在 `t_refund_order` 中有独立记录：

```text
refund_order_id
pay_order_id
mch_refund_no
refund_amount
state
channel_order_no
success_time
```

退款状态：

```text
0 INIT
1 ING
2 SUCCESS
3 FAIL
4 CLOSED
```

## 3. 支付单上的退款字段

支付单保存的是汇总：

```text
refund_amount  累计成功退款金额
refund_times   成功退款次数
refund_state   0未退款 / 1部分退款 / 2全额退款
```

退款单保存的是本次退款金额。

## 4. 退款成功时的更新

同一事务中：

```text
退款单 ING → SUCCESS
支付单 refund_times + 1
支付单 refund_amount + 本次退款金额
更新 refund_state
全额退款时支付单 SUCCESS → REFUND
```

数据库更新还带有条件：

```text
原支付状态必须为 SUCCESS
累计退款金额不能超过原支付金额
退款汇总状态不能已经全额退款
```

## 5. 异常兜底

- 退款请求超时：保持 `ING`，查原退款渠道；
- 退款成功但本地事务失败：按退款单查询并补写支付单累计；
- 退款重复回调：条件更新防重复；
- 结算后退款：需要商户余额扣回或形成欠款。

【背诵结论】

> 支付是一笔对多笔退款，每次退款有自己的渠道状态、渠道单号、失败原因和通知，因此必须有独立退款单。支付单只保存累计退款金额、次数和汇总状态。

# 问题五：并发退款如何保证不超退？

## 1. Jeepay 当前的防线

【Jeepay 现状】

申请退款时会检查：

- 原支付状态为 `SUCCESS`；
- 当前没有处理中退款；
- 累计成功退款金额加本次金额不超过原支付金额；
- 商户退款单号不重复。

退款成功回写支付单时，SQL 再次带金额条件：

```text
state = SUCCESS
AND refund_amount + 本次退款 <= amount
AND refund_state IN (0, 1)
```

这能防止支付单累计字段被更新到超过原支付金额。

## 2. 仍然存在的并发窗口

两个并发退款请求可能同时完成“是否存在处理中退款”的查询，都认为当前没有在途退款，然后都去调用渠道。

【风险】

数据库最终可以阻止累计金额超限，但此时渠道退款可能已经发生。

## 3. 生产正确方案

推荐在调用渠道前预占退款额度：

1. 开启数据库事务；
2. 锁定原支付单或退款额度账户；
3. 查询剩余可退金额；
4. 原子冻结本次退款金额；
5. 创建退款单；
6. 调用渠道；
7. 渠道明确失败时释放冻结；
8. 渠道明确成功时冻结转已退款；
9. 渠道未知时保持冻结并查询；
10. 日终对账修正。

## 4. 幂等键

```text
商户号 + 商户退款单号
```

必须唯一。

同一退款重复请求不能调用两次渠道。

【背诵结论】

> Jeepay 当前通过在途查询和成功回写金额条件降低超退风险，但申请阶段仍存在并发窗口。生产系统必须在调用渠道前用行锁或退款额度冻结完成原子预占，才能在资金外呼前真正防止并发超退。

# 问题六：转账超时为什么不能直接重发？

## 1. 转账是独立出款

`t_transfer_order` 表示 Jeepay 主动向：

- 微信零钱；
- 支付宝账户；
- 银行卡；

等目标账户出款。

它和退款不同：

- 退款必须关联原支付；
- 转账不关联原支付；
- 转账最终动作是实际出款。

## 2. 超时可能意味着什么

```text
渠道没有收到请求
渠道收到但处理失败
渠道已经成功出款，但响应丢失
渠道处理中
```

支付中心仅凭“HTTP 超时”无法区分。

如果直接改失败并重新发起，可能：

```text
第一笔已经成功
第二笔又成功
→ 重复出款
```

## 3. 正确处理

```text
保持转账单 ING
→ 使用原平台转账单号查询
→ 明确成功：更新 SUCCESS
→ 明确失败：更新 FAIL
→ 仍未知：继续查询和告警
```

## 4. Jeepay 当前补单边界

【Jeepay 现状】

- 每分钟运行转账补单；
- 只扫描创建时间在最近一天内且状态为 `ING` 的转账单；
- 没有转账过期关闭任务；
- `CLOSED=4` 没有实际业务写入；
- 没有商户余额冻结和出款账务。

超过一天仍为 `ING` 的转账不会继续被该任务自动查询，需要人工处理。

【背诵结论】

> 转账超时是结果未知，不是转账失败。必须按原平台转账单号查询原渠道，只有明确失败后才能重新出款；不能通过更换平台单号重发，否则可能重复出款。

# 问题七：分账和结算有什么区别？

## 1. 分账

分账解决：

> 一笔支付收入在商户、平台、服务商、门店、供应商等参与方之间怎么分。

Jeepay 的可分配金额：

```text
支付金额
- 商户手续费
- 已退款金额
- 已成功分账金额
```

分账记录：

```text
t_pay_order_division_record
```

## 2. 结算

结算解决：

> 可结算资金按什么周期、什么规则真正打给商户或参与方。

结算要考虑：

- 对账；
- 账务确认；
- 冻结期；
- 风险预留；
- 账期；
- 结算账户；
- 出款和银行回单。

## 3. 举例

用户支付 100 元：

```text
商户手续费 0.60
平台分账 20.00
商户剩余 79.40
```

分账只决定：

```text
20 元归平台
79.40 元归商户
```

结算才决定：

```text
平台什么时候结 20 元
商户什么时候结 79.40 元
是否要冻结一部分
银行是否实际到账
```

【Jeepay 现状】

- 有分账；
- 没有完整结算；
- 分账成功不代表接收方资金已到账。

【背诵结论】

> 分账决定“钱归谁”，结算决定“什么时候结、实际有没有到账”。分账不等于结算。

# 问题八：分账父状态结束为什么不代表全部成功？

## 1. 一次分账包含多个接收方

一个支付单可能同时分给：

```text
服务商
平台
门店
供应商
```

每个接收方都有自己的分账记录。

## 2. 父订单状态

`t_pay_order.division_state`：

```text
0 未分账
1 等待任务
2 分账处理中
3 本轮任务结束
```

状态 `3` 只表示：

> 本轮分账执行流程已经结束。

## 3. 单条记录状态

`t_pay_order_division_record.state`：

```text
0 WAIT 待分账
1 SUCCESS 明确成功
2 FAIL 明确失败
3 ACCEPT 渠道已受理
```

因此一轮任务结束后可能：

```text
接收方A SUCCESS
接收方B FAIL
接收方C ACCEPT
```

## 4. 正确处理

- 父订单只负责控制本轮任务；
- 真实资金结果按分账记录逐条判断；
- 失败记录可以人工重试；
- 已受理记录继续查询；
- 只有成功记录才能进入可结算金额；
- 失败重发要生成新的批次号。

【背诵结论】

> `division_state=3` 是任务结束，不是全部接收方成功。每个接收方必须分别看 `t_pay_order_division_record.state`。

# 问题九：支付订单如何进入复式记账？

## 1. Jeepay 当前没有复式记账

【Jeepay 现状】

- `t_pay_order` 记录交易；
- `t_refund_order` 记录退款；
- `t_pay_order_division_record` 记录分账；
- 没有账务事件、会计凭证和分录表；
- 没有商户余额账户。

## 2. 生产账务链路

```text
支付成功事件
→ 账务事件
→ 会计凭证
→ 借贷分录
→ 账户余额
→ 对账和结算
```

## 3. 简化支付分录

假设：

```text
用户支付 100 元
商户手续费 0.60 元
渠道成本 0.38 元
```

支付成功：

```text
借：渠道清算应收     100.00
    贷：商户待结算     99.40
    贷：手续费收入      0.60
```

渠道扣成本后到账：

```text
借：银行存款          99.62
借：渠道成本           0.38
    贷：渠道清算应收   100.00
```

商户结算：

```text
借：商户待结算        99.40
    贷：银行存款       99.40
```

是否为总额法或净额法，必须根据平台是否为交易主要责任人、是否控制资金和真实合同判断。

## 4. 退款记账

结算前退款：

- 冲减商户待结算；
- 冲减渠道应收；
- 手续费是否退回按合同处理。

结算后退款：

- 从商户余额或后续结算扣回；
- 余额不足形成商户欠款；
- 不修改原支付分录；
- 用新的退款或冲正凭证记录。

## 5. 幂等

每笔支付、退款、分账、结算必须生成唯一账务事件：

```text
事件类型 + 来源系统 + 来源交易号 + 版本
```

重复回调不能重复生成分录。

【背诵结论】

> 支付订单不是账务分录。生产系统要把支付、退款、手续费、分账、结算转换为唯一账务事件，再生成借贷平衡、不可篡改的凭证和分录，余额由账务明细汇总。

# 问题十：对账发现差异后为什么不能直接修订单？

## 1. 渠道账单不是永远绝对正确

差异可能来自：

- 本地订单号映射错误；
- 渠道文件延迟；
- 账单重复导入；
- 状态口径不同；
- 金额单位错误；
- 渠道重复交易；
- 本地重复记录；
- 渠道账单自身修正；
- 跨日交易；
- 人工误操作。

## 2. 直接改订单会丢失证据

如果直接：

```text
CLOSED → SUCCESS
FAIL → SUCCESS
```

会绕过：

- 渠道真实回执；
- 商户通知；
- 账务调整；
- 分账和结算影响；
- 操作人审批；
- 历史状态审计。

## 3. 正确处理流程

```text
发现差异
→ 确认文件和账单完整性
→ 按渠道订单号或平台订单号匹配
→ 分类差异
→ 查询渠道证据
→ 判断本地或渠道原因
→ 自动修复或人工审核
→ 修复业务状态
→ 生成账务调整
→ 复核余额和资金
→ 关闭差错工单
```

## 4. 可自动修复的安全场景

- 本地 `ING`，渠道明确成功且金额一致；
- 回调丢失，主动查询结果一致；
- 通知未发送，但支付状态已经明确；
- 对账重复执行，通过批次幂等识别。

## 5. 必须人工处理的场景

- 金额不一致；
- 商户身份不一致；
- 本地成功渠道无；
- 渠道成功本地无；
- 重复扣款；
- 结算已出款后的重大差异；
- 风险冻结或司法争议。

【背诵结论】

> 对账负责发现差异，不是直接覆盖订单。必须先确认账单、分类差异、获取渠道证据，再按补单、退款或调账流程处理，并保留完整审计链。

# 问题十一：结算后的退款从哪里扣钱？

## 1. 结算前后完全不同

### 结算前退款

交易还在待结算余额中：

```text
直接从待结算金额扣减
```

商户尚未实际收款，不需要向商户追偿。

### 结算后退款

钱已经打给商户，平台仍向用户退款：

```text
平台先退款
→ 从商户可结算余额扣回
```

如果可结算余额不足：

- 冻结后续结算；
- 下期结算抵扣；
- 形成商户欠款；
- 使用风险准备金；
- 人工追偿。

## 2. 余额状态

推荐账户至少区分：

```text
待结算余额
可结算余额
冻结余额
已结算余额
商户欠款
```

退款扣款不能直接修改已结算历史金额，应新增退款或冲正账务事件。

## 3. Jeepay 当前能力

【Jeepay 现状】

Jeepay 只能按原支付单发起退款，并更新退款累计金额；没有商户资金账户、可结算余额和结算后追偿模块。

【背诵结论】

> 结算前退款扣减待结算款；结算后退款从商户可结算余额、下期结算、冻结资金或欠款账户扣回。Jeepay 当前只有退款交易能力，没有完整的结算后退款追偿体系。

# 问题十二：如何防止同一交易重复进入结算？

## 1. 唯一账务事件

每笔支付、退款、分账和调整形成唯一账务事件：

```text
UNIQUE(event_type, source_type, source_id, source_version)
```

重复回调或重复批处理不能生成多个有效事件。

## 2. 结算明细唯一占用

同一个账务事件在有效结算范围内只能被占用一次。

概念约束：

```text
UNIQUE(accounting_event_id, active_settlement_scope)
```

如果数据库很难表达条件唯一索引，可以建立事件占用表。

## 3. 结算批次幂等

```text
UNIQUE(cycle_code, business_date, account_id, currency)
```

同一批次重复执行：

- 识别已有批次；
- 校验输入水位；
- 不重复生成已审批批次；
- 重新计算生成新版本，不覆盖历史。

## 4. 结算单和出款单幂等

```text
结算单：商户 + 账期 + 币种唯一
出款单：结算单 + 收款账户 + 币种唯一
```

## 5. 固定输入水位

清分和结算必须锁定数据截止时间：

- 只读取水位之前的事件；
- 水位之后进入下一期；
- 迟到交易通过补结或调整处理；
- 不因任务重跑读取到新数据而改变历史批次。

## 6. Jeepay 当前能力

【Jeepay 现状】

Jeepay 没有结算批次和结算明细，因此只能提供支付交易唯一键，无法单独防止结算重复。

【背诵结论】

> 防止重复结算要同时依靠唯一账务事件、结算明细唯一占用、结算批次唯一键、固定输入水位和出款单幂等，不能只靠任务执行一次。

# 问题十三：出款成功后退票怎么处理？

## 1. 渠道成功不等于最终到账

出款接口返回成功可能只是：

```text
渠道已受理
银行已接收指令
```

之后仍可能：

- 收款账户不存在；
- 账户状态异常；
- 户名不一致；
- 银行退票；
- 收款机构退回。

## 2. 退票处理

```text
出款单 SUCCESS
→ 银行或渠道返回退票
→ 出款单进入 RETURNED
→ 冲回银行存款
→ 恢复商户应付或形成商户欠款
→ 检查是否需要重新出款
```

## 3. 重新出款

必须先确认：

- 原出款已经真正退回；
- 原出款不可能再次成功；
- 账户信息已经修正；
- 使用新的出款指令或新版本；
- 保留原出款和退票的完整关联。

## 4. Jeepay 当前能力

【Jeepay 现状】

- 有转账单；
- 没有完整结算出款单；
- 没有银行退票处理；
- 没有出款资金账务；
- `CLOSED=4` 没有实际写入。

【背诵结论】

> 出款渠道成功只是受理或初步成功，最终要以银行回单为准。退票后要冲回银行资金、恢复商户应付或形成欠款，原出款和退票都要保留，不能直接重复打款。

# 问题十四：MQ 为什么不能保证只消费一次？

## 1. MQ 通常是至少一次投递

常见原因：

- 消费者处理成功但 ACK 丢失；
- 网络抖动；
- 消费者重启；
- 消息重试；
- 多实例竞争；
- 生产端重复发送。

因此消息可能被处理多次。

## 2. Jeepay 的 MQ 场景

- 支付延迟查单；
- 商户通知；
- 自动分账；
- 配置缓存刷新；
- 登录缓存清理。

## 3. 业务幂等

消费者不能相信“消息只来一次”，必须：

- 重新查询数据库当前状态；
- 使用状态条件更新；
- 通知记录唯一；
- 分账记录条件更新；
- 账务事件唯一；
- 重复消息不重复执行资金副作用。

## 4. 当前实现风险

【Jeepay 现状】

- 多个 MQ Receiver 使用异步线程；
- MQ 查单次数只放在消息体中，没有数据库持久化；
- 通知延迟重试依赖 MQ；
- 状态更新和消息发送没有统一事务 Outbox。

【生产补全】

- 本地事务写 Outbox；
- 发布器扫描发送；
- 消费端幂等；
- 死信队列；
- 定期补偿扫描；
- 人工重放工具。

【背诵结论】

> MQ 解决异步和解耦，不解决业务恰好一次。支付系统必须以至少一次投递为前提，用数据库唯一约束、状态 CAS、Outbox 和补偿任务保证重复消息不产生重复资金副作用。

# 问题十五：晚到支付、重复回调和本地状态冲突怎么处理？

## 1. 先确认渠道事实

收到晚到成功回调：

1. 验证渠道签名；
2. 校验平台订单号、渠道订单号、商户和应用；
3. 校验金额和币种；
4. 主动查询渠道；
5. 保存原始回调证据。

## 2. 不能直接忽略

本地可能已经是：

```text
CLOSED
FAIL
SUCCESS
REFUND
```

不同状态处理不同。

### 本地 `ING`

正常条件更新：

```text
ING → SUCCESS
```

### 本地 `SUCCESS`

处理为重复成功：

- 不重复改状态；
- 不重复通知；
- 不重复分账；
- 不重复记账；
- 返回渠道 ACK。

### 本地 `CLOSED`

这是晚到支付：

- 保留原关闭记录；
- 查询渠道确认支付成功；
- 进入差错队列；
- 判断商户业务是否已履约；
- 未履约时决定补履约或退款；
- 不能直接覆盖状态抹掉审计。

### 本地 `REFUND`

检查退款是否已经完成：

- 如果重复成功回调，不能恢复可支付；
- 如果退款状态和渠道不一致，进入差错。

## 3. 判断商户是否履约

Jeepay 不掌握商品、库存、会员或券码履约状态，需要商户业务系统提供查询接口。

可能的结论：

```text
已履约：不重复发货，修复支付事实并补账
未履约但允许履约：修复支付成功后通知商户履约
未履约且不允许履约：修复支付成功后发起退款
库存不足：退款
无法确定：保持异常，人工处理
```

## 4. 异常处理原则

- 不从支付回调线程里长期阻塞；
- 先可靠持久化异常事件；
- 返回渠道 ACK；
- 异步查询渠道和商户；
- 按业务规则补履约或退款；
- 所有状态变更留审计；
- 日终对账再次确认。

【Jeepay 现状】

- 支付回调主要处理 `ING`；
- 过期任务会把本地 `INIT/ING` 直接改 `CLOSED`；
- 没有标准的晚到支付补偿流程；
- 没有商户履约查询能力；
- 没有完整异常工单和账务调整。

【背诵结论】

> 晚到成功不能按重复回调简单丢弃。必须先验签并查渠道，再检查本地状态和商户履约。已履约只补支付事实，不重复发货；未履约按业务规则补履约或退款；状态冲突和无法判断进入异常队列。Jeepay 当前缺少完整的 `CLOSED → SUCCESS` 晚到支付流程，需要生产化补全。

# 附：十五个问题的极简口述版

1. 支付成功、通知成功、记账成功和结算成功是四个不同事实。
2. 回调可能重复和乱序，所以支付状态必须用旧状态 CAS 推进。
3. 商户查询看 Jeepay 本地记录，渠道查询获取支付机构真实结果。
4. 退款一笔对多笔，必须有独立退款单。
5. 并发退款要在调用渠道前原子冻结额度，不能只先查后改。
6. 转账超时先查原转账单，绝不能换单号重复出款。
7. 分账决定钱归谁，结算决定何时出款和是否到账。
8. 分账父状态结束只代表任务结束，具体看每条接收方记录。
9. 支付订单要生成账务事件、借贷分录和余额，订单本身不是账。
10. 对账负责发现差异，不能直接用渠道数据覆盖订单。
11. 结算前退款扣待结算款，结算后退款扣余额、下期结算或形成欠款。
12. 防止重复结算依靠唯一事件、唯一结算占用、批次幂等和固定水位。
13. 出款成功仍要核对银行回单，退票后冲回资金并恢复商户应付。
14. MQ 是至少一次投递，业务必须通过 CAS、唯一键和 Outbox 幂等。
15. 晚到成功先查渠道和商户履约，再决定补履约、退款或人工处理。
