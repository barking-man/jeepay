### 1. 为什么用 MySQLDump 迁移，而不是 DTS？了解 Binlog 增量同步吗？

**对应时间：** 00:10:33–00:11:53

**面试官的问题：**

> 为什么用 MySQLDump 迁移，不用 DTS 相关的技术？接触过 DTS 吗？

**当时的回答：**

> 没怎么了解过，因为 MySQLDump 是自带的工具，可以直接拿来用。

**参考答案：**

MySQLDump 可以用来做存量快照，但它本身不是完整的“不停机迁移方案”。它没有持续捕获源库新增和修改数据的能力；在大数据量或使用不当时，还会带来长时间读取、锁表、备份文件过大、恢复慢等问题。

DTS 这类数据传输服务的核心价值，是完成“全量初始化 + 增量追平 + 校验 + 切换”：

1. 在源库记录一个一致性位点，例如 GTID 或 Binlog Position。
2. 按该位点导出全量快照。
3. 从同一位点开始捕获 Binlog，持续同步快照期间产生的新增和变更。
4. 当增量延迟接近 0 后，做行数、主键、摘要或抽样校验。
5. 先切只读流量，再短暂停写或在双写状态下完成最终追平。
6. 确认数据一致后切写流量；保留反向同步或回滚窗口。

如果不用云上的 DTS，也可以用 Debezium、Canal 或自建 Binlog 消费程序实现 CDC。MySQLDump 只能承担其中的全量阶段；如果还要使用它，至少要使用一致性快照，例如 `--single-transaction`，并按表或数据块拆分导出，避免长事务和大文件恢复。

可以这样收口：

> 我现在会优先用 DTS 或 CDC 做“全量快照加 Binlog 增量追平”。MySQLDump 更适合小数据量的初始快照，不能单独保证迁移期间的新写入也被同步。切换前必须有延迟监控、数据校验和可回滚方案。

**记忆关键词：**

`一致性位点 → 全量快照 → Binlog 增量 → 数据校验 → 灰度切流 → 保留回滚`

### 2. Nacos 的服务注册、健康检查和配置刷新是怎么实现的？

**对应时间：** 00:19:42–00:22:31

**面试官的问题：**

> Nacos 怎么注册服务？怎么做健康检查？配置如何更新和刷新？

**当时的回答：**

> 会引入依赖、配置地址和命名空间，服务启动后会注册；再解释到原理时回答“没怎么了解”。

**参考答案：**

先说服务注册：

1. Spring Cloud Alibaba 的 `NacosServiceRegistry` 在应用注册阶段调用 Nacos Client 的 `registerInstance`。
2. 注册信息包含 namespace、group、service、cluster、IP、端口、权重、元数据以及是否为临时实例。
3. Nacos 2.x 主要通过 gRPC 长连接通信；服务端保存实例信息，并把变更推送给订阅该服务的客户端。
4. 消费者通过服务名获取健康实例列表，再交给 Spring Cloud LoadBalancer 选择实例。

再说健康检查：

- 临时实例由客户端维持心跳。默认心跳间隔通常是 5 秒；服务端超过一段时间没收到心跳会先标记不健康，再在更长时间后删除实例。
- 非临时实例通常由服务端主动探测，连接或探测结果异常时会更新实例状态。
- 应用正常关闭时会主动注销；异常断开时，由心跳超时和连接失效完成兜底清理。

最后说配置刷新：

1. 客户端按 namespace、group、dataId 订阅配置。
2. Nacos 1.x 使用长轮询核对 MD5；Nacos 2.x 通过 gRPC 长连接接收配置变更通知。
3. 客户端发现 MD5 或版本变化后拉取完整配置，更新本地快照。
4. Spring Cloud Alibaba 发布配置变更事件，触发 `@RefreshScope` Bean 重建，使带有 `@Value` 或 `@ConfigurationProperties` 的配置生效。
5. 不是所有 Bean 都会重建，也不是每个应用各自读文件；通常由 Nacos Client 统一监听，再将变化传播给 Spring 容器。

可以这样收口：

> 我实际使用时主要负责接入和配置，原理上还需要补齐两点：服务注册依赖 Nacos Client 和长连接，临时实例依靠心跳维持健康状态；配置刷新则依靠订阅通知、MD5 或版本变更检查，以及 Spring 的事件和 RefreshScope 完成动态生效。

**记忆关键词：**

`registerInstance → gRPC/心跳 → 实例状态 → 变更推送 → 拉取配置 → RefreshEvent`

### 3. 现场实现一个 LRU 缓存

**对应时间：** 00:38:21–00:59:17

**面试要求：**

- 支持 `get(key)`：存在时返回 value，并标记为最近使用；不存在返回 `-1`。
- 支持 `put(key, value)`：插入或更新；容量满时淘汰最久未使用的元素。
- 时间复杂度越低越好。

**当时的回答：**

你想到“哈希表 + 列表”，方向是对的，但实现和演示存在以下问题：

- 没有明确把 `put` 插入或更新的元素标记为最近使用。
- 淘汰顺序没有讲清楚，最终被面试官指出“淘汰的不是最早元素”。
- 如果用普通 `ArrayList`，按元素查找、删除和移动都可能退化到 O(n)，无法达到面试官要求的 O(1)。
- 现场演示没有覆盖“容量已满后再次 put”这个最关键的路径。

**参考代码：**

```java
import java.util.HashMap;
import java.util.Map;

class LRUCache {
    private static class Node {
        int key;
        int value;
        Node prev;
        Node next;

        Node() {
        }

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, Node> cache = new HashMap<>();
    private final Node head = new Node();
    private final Node tail = new Node();

    public LRUCache(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = cache.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = cache.get(key);

        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }

        if (cache.size() == capacity) {
            Node leastRecentlyUsed = tail.prev;
            remove(leastRecentlyUsed);
            cache.remove(leastRecentlyUsed.key);
        }

        Node newNode = new Node(key, value);
        cache.put(key, newNode);
        addToHead(newNode);
    }

    private void moveToHead(Node node) {
        remove(node);
        addToHead(node);
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void addToHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }
}
```

**复杂度：**

- `get`：O(1)
- `put`：O(1)
- 空间：O(capacity)

**现场演示：**

设容量为 2：

```text
put(1, 1)      缓存：1
put(2, 2)      缓存：2 -> 1
get(1) = 1     缓存：1 -> 2
put(3, 3)      缓存：3 -> 1，淘汰 2
get(2) = -1
put(4, 4)      缓存：4 -> 3，淘汰 1
get(1) = -1
```

可做三点补充：

1. `HashMap` 负责 O(1) 定位节点，双向链表负责 O(1) 调整访问顺序和删除尾部节点。
2. 头结点一侧表示最近使用，尾结点一侧表示最久未使用。
3. 如果允许使用标准库，也可以使用 `LinkedHashMap` 的 access-order 模式，但在“考察编码能力”的题目中应先手写双向链表。

### 4. Spring Boot 自动装配是怎么实现的？

**对应时间：** 00:15:40–00:17:27

**当时的回答：**

> 会扫描并生成 BeanDefinition，把这些定义注册到 Map 中，再按依赖创建 Bean。

这个回答描述的是 Spring IoC 创建 Bean 的通用过程，但没有回答“自动装配的候选配置从哪里来、如何筛选、如何决定是否生效”。

**参考答案：**

1. `@SpringBootApplication` 中包含 `@EnableAutoConfiguration`。
2. `@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 引入自动配置选择器。
3. Spring Boot 2.x 主要通过 `SpringFactoriesLoader` 读取 `META-INF/spring.factories` 中的 `EnableAutoConfiguration` 候选类；Spring Boot 3.x 主要读取各依赖 jar 里的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。
4. `AutoConfigurationImportSelector` 对候选配置去重，处理 exclude，并按 `@AutoConfigureBefore`、`@AutoConfigureAfter`、`@AutoConfigureOrder` 排序。
5. Spring 的 `ConfigurationClassPostProcessor` 解析这些配置类。解析前后会通过 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 等条件判断是否生效。
6. 符合条件的配置类继续解析 `@Bean` 方法并注册 BeanDefinition，最后由容器实例化 Bean。

一句话总结：

> 自动装配不是“启动时扫描整个磁盘上的类”，而是先通过约定文件或 imports 文件拿到候选配置类，再用条件注解筛选，最后把符合条件的 `@Bean` 注册到 Spring 容器。

**记忆关键词：**

`@EnableAutoConfiguration → ImportSelector → imports 文件 → 条件过滤 → BeanDefinition`

### 5. Spring Cloud 的配置中心、网关和负载均衡分别怎么工作？

**对应时间：** 00:17:27–00:19:34

**当时的回答：**

你先回答“原理了解得不多”，后面只讲了新建服务、从 Nacos 拉配置、请求经过网关和路由到微服务的使用流程，没有回答三个组件各自的核心机制。

**参考答案：**

#### 配置中心

配置中心保存不同环境、不同服务的配置。客户端启动时用 `spring.application.name`、profile 和 label 等信息定位配置，拉取后合并到 Spring Environment，并保留本地缓存。配置变化时，客户端收到通知后重新拉取，再通过 RefreshEvent 和 `@RefreshScope` 更新需要动态变化的 Bean。

#### 网关

网关是所有入口流量的统一控制面，核心是“路由匹配 + 过滤器链 + 转发”：

- 路由按 Path、Host、Header、Method 等条件匹配。
- 过滤器负责鉴权、限流、日志、TraceId、请求头和响应头改写等。
- 使用 `lb://service-name` 时，网关先向注册中心获取实例，再由负载均衡器选择目标服务。

#### 负载均衡

Spring Cloud LoadBalancer 从 DiscoveryClient 或 ServiceInstanceListSupplier 获取服务实例，过滤不可用或不符合版本的实例，然后按策略选择，例如轮询、随机、加权或灰度。调用方再用选出的实例 IP、端口发起请求。重试策略必须只对幂等请求开启，否则可能放大重复写入。

可以这样收口：

> 我之前主要是配置和使用。原理上，配置中心是拉取、缓存、监听和动态刷新；网关是路由谓词加过滤器链；负载均衡是从注册中心获取实例后，按策略选出目标实例并转发。

**参考答案：**

> 遇到过共享 Redis 被其他业务影响的情况。另一个团队上线后写入了一批大对象，导致 Redis 的响应延迟升高，我们业务开始出现超时。排查时我先看监控和告警，确认是 Redis 延迟上升，再通过慢日志、命令统计、Key 大小和网络及集群指标定位到异常写入。短期处理是回滚或关闭对应功能、清理异常 Key，避免继续放大。长期方案是按业务隔离实例，至少也要为 Key 大小、过期时间、写入吞吐设限制，并补充大 Key、热 Key、慢日志和延迟监控。不能把“命名空间前缀不同”误认为资源隔离。

- 不要使用 `KEYS *` 扫描整个实例。
- 大对象尽量拆分、压缩或设置较短 TTL。
- 删除大 Key 时优先用 `UNLINK`，避免 `DEL` 同步释放给主线程造成抖动。

**这题的价值：** 回答要讲出“现象、定位、短期止损、根因、长期治理”，不要只讲最终改了什么配置。

## 四、面试表达上的改进

1. **先给结论，再展开细节。** 被问“怎么实现”时，先回答核心机制，再讲项目中的使用方式。
2. **不会时不要只答“没怎么了解”。** 可以回答：“我没有在生产环境落地过，但我理解它的核心是把全量快照和增量同步衔接起来。”这样仍然可以展示推理能力。
3. **简历上的技术栈必须至少准备“用途、关键机制、一个线上问题和边界”四件事。**
4. **编码题先讲不变量。** LRU 的不变量是“哈希表定位节点，双向链表维护访问顺序，尾部节点是淘汰候选”；讲完不变量再写代码，能显著降低现场出错的概率。
5. **项目问题统一使用 STAR。** 背景、目标、动作、结果都要有数字；避免只描述“我做了什么”而缺少结果。
