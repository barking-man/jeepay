# 四、项目背景与整体架构

Jeepay 是面向普通商户和服务商模式的聚合支付交易平台。

核心模块：

```text
jeepay-payment     支付网关
jeepay-merchant    商户后台
jeepay-manager     运营后台
jeepay-service     数据库业务实现
jeepay-core        实体、常量和工具
jeepay-components  MQ、OSS 等公共组件
```

核心依赖：

- Spring Boot 3.3.7；
- JDK 17；
- Spring Security；
- MyBatis-Plus；
- MySQL；
- Redis；
- RocketMQ、ActiveMQ 或 RabbitMQ；
- 微信、支付宝、云闪付等渠道 SDK。

整体采用同步 API 加异步补偿：

```text
商户同步调用支付中心
→ 支付中心同步调用渠道
→ 用户完成支付
→ 渠道异步回调
→ 支付中心主动查单兜底
→ 支付中心异步通知商户
→ 延迟 MQ 和定时任务补偿长期未决
```

## 5.1 商户和渠道

| 表 | 作用 |
|---|---|
| `t_isv_info` | 服务商 |
| `t_mch_info` | 普通商户或特约商户 |

## 5.3 三类订单号


# 六、重点业务固化知识

## 6.1 为什么订单先落库再调渠道

支付中心先以 `INIT` 保存本地支付单，再调用渠道。

原因：

- 固定平台订单号；
- 提供渠道调用幂等键；
- 外部超时后可按订单号查单；
- 回调可关联本地订单；
- 后续退款、通知、分账和对账都有稳定主键。

数据库与外部渠道无法组成一个事务，因此只能使用状态机、查单、补偿和对账保证最终一致。

## 6.2 渠道响应分类

| 渠道响应 | 本地处理 |
|---|---|
| 明确成功 | 成功终态 |
| 明确失败 | 失败终态 |
| 处理中 `WAITING` | `ING` |
| 结果未知 `UNKNOWN` | `ING` |
| 渠道接口异常 | `ING` |
| 支付中心自身异常 | 可能保留 `INIT` |

核心原则：

> 超时不是失败，未知不是失败，没有渠道证据不能补成功。

## 6.3 `ING` 与支付参数

`ING` 表示结果未定，不表示一定拿到支付参数。

如果渠道已创建订单并返回：

- `code_url`；
- `prepay_id`；
- App 参数；

则可以返回给商户让用户付款。

如果渠道调用超时、支付参数丢失，则只能后台查询原渠道，不能凭本地记录生成新支付参数，也不能换单号重下。

## 6.4 支付状态机

```text
0 INIT
1 ING
2 SUCCESS
3 FAIL
4 CANCEL，已定义但当前未实际写入
5 REFUND
6 CLOSED
```

主要迁移：

```text
INIT → ING
INIT/ING → SUCCESS/FAIL
INIT/ING → CLOSED
SUCCESS → SUCCESS       部分退款
SUCCESS → REFUND        累计全额退款
```

所有迁移使用旧状态条件，防止重复回调覆盖终态。

## 6.5 退款状态机

```text
0 INIT
1 ING
2 SUCCESS
3 FAIL
4 CLOSED
```

退款成功必须在同一事务中：

```text
退款单 ING → SUCCESS
支付单 refund_times + 1
支付单 refund_amount + 本次退款金额
更新 refund_state
全额退款时支付主状态 SUCCESS → REFUND
```

退款单的 `refund_amount` 是本次退款金额。

支付单的 `refund_amount` 是所有成功退款的累计金额。

## 6.6 转账状态机

```text
0 INIT
1 ING
2 SUCCESS
3 FAIL
4 CLOSED，已定义但当前未实际写入
```

转账与退款不同：

- 不关联原支付；
- 向指定账户出款；
- 超时可能已经成功；
- 必须按原转账单号查原渠道；
- 不能换单号重复出款。

## 6.7 分账状态

父订单：

```text
0 未分账
1 等待任务
2 处理中
3 本轮任务结束
```

分账明细：

```text
0 WAIT
1 SUCCESS
2 FAIL
3 ACCEPT
```

`division_state=3` 只表示本轮任务结束，不代表所有接收方成功。

## 6.8 分账与结算

```text
分账：决定交易收入归谁
结算：决定什么时候真正出款
```

分账成功后仍要等待对账、账期、冻结和结算。

# 七、渠道回调、查询与通知

## 7.1 渠道回调

回调处理必须：

1. 验签；
2. 校验渠道商户或应用；
3. 校验平台订单号；
4. 校验金额和币种；
5. 检查交易类型；
6. 使用旧状态条件更新；
7. 返回渠道要求的 ACK。

验签通过不代表业务字段匹配。

## 7.2 商户查询与渠道查询

```text
商户查询：读取 Jeepay 本地订单
渠道查询：向支付宝、微信等查询真实状态
```

商户查询不能替代内部补单。

## 7.3 当前补偿时限

| 项目 | 当前规则 |
|---|---|
| 支付单默认过期 | 2 小时 |
| 退款单默认过期 | 2 小时 |
| 支付 MQ 查单首次延迟 | 5 秒 |
| 单条 MQ 链最多查询 | 6 次 |
| 支付定时补单 | 每分钟，扫描创建超过 10 分钟的 `ING` |
| 退款定时补单 | 每分钟扫描 `ING` |
| 转账定时补单 | 每分钟扫描最近一天内创建的 `ING` |
| 自动分账延迟 | 80 秒 |
| 分账受理查询 | 创建超过 5 分钟 |
| 商户通知重试 | 默认 6 次 |
| 通知延迟 | 30/60/90/120/150 秒 |
| 通知 HTTP 超时 | 20 秒 |

## 7.4 MQ 查单重要细节

支付 MQ 接收器只在查询结果：

- 为空；
- 没有渠道状态；
- 为 `WAITING`；

时继续发送下一条延迟消息。

查询结果 `UNKNOWN` 时，当前 MQ 链不继续，后续主要依赖分钟级扫描。

## 7.5 商户通知

商品通知记录唯一：

```text
order_id + order_type
```

`order_type`：

```text
1 支付
2 退款
3 转账
```

通知失败不能回滚支付，只能重试或人工补发。

# 八、退款并发与预占

## 8.1 当前风险

Jeepay 退款申请大致为：

```text
查询支付单
→ 检查退款状态和累计金额
→ 查询是否有 ING 退款
→ 保存退款单
→ 调用渠道
```

申请阶段没有支付单行锁，也没有原子退款额度预占。

两个并发请求可能同时：

```text
看到累计退款20元
看到没有 ING 退款
各自判断20+60<=100
都调用渠道退款60元
```

最终渠道退款140元，但本地金额 SQL 在退款成功回写时才会阻止累计超100元。

## 8.2 正确方案

短事务：

```text
锁定支付单
→ 校验支付状态 SUCCESS
→ 校验已退款 + 已预占 + 本次退款 <= 支付金额
→ 创建退款单
→ 原子增加退款预占金额
→ 提交
```

提交后再调用渠道。

结果：

```text
明确成功：预占转已退款
明确失败：释放预占
超时/未知：保持预占
```

支付单可以增加：

```text
refund_reserved_amount
```

或使用独立退款额度预占表。

## 8.3 原子更新是关键

错误写法：

```text
SELECT 预占金额
→ Java 判断
→ UPDATE 写回
```

正确写法：

```text
UPDATE pay_order
SET refund_reserved_amount = refund_reserved_amount + 本次金额
WHERE pay_order_id = ?
AND state = SUCCESS
AND refund_amount + refund_reserved_amount + 本次金额 <= amount
```

只有更新行数为 1 才能调用渠道。

字段本身不防并发，数据库原子更新或 `SELECT ... FOR UPDATE` 才防并发。

# 九、晚到支付与履约

## 9.1 晚到支付定义

```text
本地订单已经 CLOSED/FAIL
渠道后来明确支付成功
```

## 9.2 处理流程

```text
验签
→ 主动查渠道
→ 保存晚到支付异常
→ 查询商户履约状态
```

### 已履约

- 补记支付成功事实；
- 不重复发货或开通权益；
- 补通知；
- 补账务；
- 进行审计。

### 未履约，业务允许履约

- 补记支付成功；
- 通知商户按业务订单幂等履约。

### 未履约，业务不允许履约或库存不足

- 补记支付成功；
- 创建独立退款单；
- 原路退款；
- 补账务。

### 无法判断

- 保持异常；
- 人工处理。

## 9.3 Jeepay 当前边界

Jeepay 只负责支付和通知，不掌握：

- 发货；
- 库存；
- 会员开通；
- 券码核销；
- 服务是否完成。

“商户是否履约”需要商户业务系统提供状态查询或人工确认。

当前 Jeepay 没有标准 `CLOSED → SUCCESS` 晚到支付补单流程，也没有履约查询模块。

# 十、撤销、关单与退款

## 10.1 三者区别

```text
关单：阻止未支付订单继续付款
撤销：取消授权或撤销未完成交易
退款：退回已成功支付资金
```

## 10.2 当前 Jeepay

- 有关单；
- 有退款；
- `CANCEL=4` 已定义但未实际写入；
- 没有统一撤销接口；
- 微信返回 `REVOKED` 时当前映射为明确失败；
- MQ 查单达到上限后的撤销调用仍是 TODO。

## 10.3 生产撤销流程

```text
校验原支付和商户
→ 判断渠道和交易阶段是否支持撤销
→ 发起撤销
→ 成功、失败或未知
→ 未知主动查询
→ 已清算或不支持撤销则转退款
```

未扣款撤销：

- 只释放授权冻结；
- 不需要资金退款冲正。

已扣款撤销：

- 如果已经生成应收、应付或收入，生成反向账务分录。

撤销和退款必须串行互斥。

# 十一、账务、清分与结算

## 11.1 四个不同事实

```text
支付成功：渠道确认交易
通知成功：商户收到结果
记账成功：账务分录已生成
结算成功：资金已出款并到账
```

## 11.2 简化支付分录

用户支付100元，商户手续费0.60元：

```text
借：渠道清算应收       100.00
    贷：商户待结算      99.40
    贷：手续费收入       0.60
```

渠道成本0.38元，实际到账99.62元：

```text
借：银行存款           99.62
借：渠道成本            0.38
    贷：渠道清算应收    100.00
```

商户结算99.40元：

```text
借：商户待结算         99.40
    贷：银行存款        99.40
```

## 11.3 账务原则

- 支付订单不是会计分录；
- 借贷必须平衡；
- 账务事件必须唯一；
- 分录不可修改；
- 错误用反向分录冲正；
- 余额可由分录重算核对；
- 支付成功不等于已经记账；
- 结算成功不等于已经到账。

## 11.4 清分

清分计算各方应收应付：

```text
商户收入
= 支付金额
- 商户手续费
- 退款
- 分账
- 冻结或预留
+ 调账
```

## 11.5 结算

结算需要：

- 支付成功；
- 渠道对账；
- 账务确认；
- 满足账期；
- 无冻结；
- 未被其他结算单占用；
- 商户账户正常。

## 11.6 结算后退款

```text
扣商户可结算余额
→ 不足则下期结算抵扣
→ 或形成商户欠款
→ 或使用风险准备金
```

Jeepay 当前没有商户余额、结算和追偿模块。

# 十二、对账模块固化知识

## 12.1 基本原则

对账不是用本地渠道订单号逐笔查询，而是：

```text
按账单业务日下载渠道完整明细
+
读取平台本地交易
→ 分类
→ 匹配
→ 比较字段
→ 生成差异
```

## 12.2 账单类型

最低需要：

- 支付明细；
- 退款明细；
- 手续费明细。

有扩展能力后还需要：

- 分账；
- 转账或代付；
- 冲正；
- 拒付；
- 银行退票；
- 结算资金账单。

## 12.3 账单状态

不能只拉成功记录，应按渠道提供的全部状态拉取。

支付可能包含：

- 成功；
- 关闭；
- 失败或撤销；
- 退款或部分退款。

退款可能包含：

- 处理中；
- 成功；
- 失败；
- 关闭。

转账可能包含：

- 处理中；
- 成功；
- 失败；
- 银行退回。

## 12.4 支付与退款分开对账

```text
渠道支付明细 ↔ t_pay_order
渠道退款明细 ↔ t_refund_order
```

退款不能直接对支付单。

退款匹配优先级：

1. 渠道退款交易号 ↔ `t_refund_order.channel_order_no`；
2. 原渠道支付交易号 + 商户退款单号；
3. 原渠道支付交易号 + 退款金额 + 时间窗口，作为辅助。

逐笔退款匹配后，再通过 `pay_order_id` 汇总，校验：

```text
支付单 refund_amount
支付单 refund_times
支付单 refund_state
```

## 12.5 平台有、渠道暂时无

首次发现：

```text
标记 PENDING_CHANNEL
不直接进入正式短款
```

主动查询渠道，超过渠道迟到窗口仍无记录后，才形成正式差异。

平台有渠道无不能直接补单，因为没有渠道成功事实。

## 12.6 渠道有、平台无

不能直接补单。

处理：

1. 按渠道交易号找本地；
2. 按平台或商户订单号找本地；
3. 判断是否重复账单行；
4. 判断是否无主支付；
5. 判断是否重复扣款；
6. 查渠道状态。

可关联本地订单时受控补状态。

无业务订单时进入无主交易，原路退款或挂账。

## 12.7 重复账单与重复扣款

### 重复账单行

```text
同一个渠道交易号、类型、金额重复出现
```

处理：文件去重，不退款。

### 真实重复扣款

```text
同一业务订单对应多个不同渠道交易号
每个渠道交易都真实成功扣款
```

处理：保留证据，多余扣款退款。

渠道交易号本身是一对一；业务订单与渠道交易在重试、组合支付或系统缺陷下可能一对多。

## 12.8 多对一和组合支付

多笔平台订单对应一笔渠道支付，必须有明确分配关系：

```text
channel_trade_no
platform_order_id
allocated_amount
```

所有分配合计必须等于渠道支付金额。

没有分配关系时不能靠金额猜测。

## 12.9 状态不一致修复

渠道状态必须先映射成 Jeepay 内部状态。

支付：

- 渠道成功、本地 ING：补成功；
- 渠道失败、本地 ING：补失败；
- 渠道成功、本地 CLOSED/FAIL：晚到支付；
- 渠道退款、本地仍成功：检查退款单，不能只改状态。

退款：

- 渠道退款成功、本地 ING：补齐退款并更新支付单累计；
- 本地退款成功、渠道失败：高风险差错；
- 本地 FAIL、渠道成功：补退款事实，防止再次退款。

转账：

- 渠道成功：补成功；
- 渠道失败：补失败；
- 银行退票：生成独立退回事件。

## 12.10 结算冻结

如果平台有、渠道始终无：

```text
标记不可结算
生成 settlement_hold
禁止进入结算
```

如果后来渠道确认成功：

```text
关闭差异
释放 hold
下一批次结算
```

如果已经错误结算：

```text
形成商户欠款
下期抵扣
人工追偿
```

当前 Jeepay 没有结算表，因此结算冻结属于扩展设计。

# 十三、最终一致性与 Outbox

## 13.1 当前问题

支付状态提交成功后，如果服务在发送 MQ 之前崩溃：

```text
支付成功
→ 通知没创建
→ 分账没触发
```

## 13.2 Outbox 方案

同一个数据库事务：

```text
更新支付/退款/转账状态
+
插入 Outbox 事件
```

事务提交后，中继程序读取 Outbox，投递到 MQ。

MQ 消费者：

- 重新查询数据库；
- 按业务单号幂等；
- 创建通知、分账、账务事件。

Outbox 解决“本地事务成功但消息丢失”，不保证消费恰好一次。

## 13.3 最适合 Outbox 的场景

- 支付成功后的商户通知和自动分账；
- 退款成功后的通知和账务；
- 转账结果后的通知和资金账务；
- 分账明细终态后的清分和账务；
- 晚到支付异常任务；
- 未来结算和出款事件。

Outbox 不适合替代同步支付渠道调用。

## 13.4 Outbox 与长期未决订单的关系

两者不是同一机制：

```text
Outbox：已经确认的状态变化可靠触发下游
定时扫描：长期没有最终状态时主动查渠道
人工升级：无法自动收敛时兜底
```

支付长期 `ING` 时可能没有成功或失败事件，Outbox 无事件可发，必须靠定时查单。

# 十四、高可用与高性能

## 14.1 当前已有

- 支付、运营、商户模块拆分；
- 数据库唯一约束；
- 状态条件更新；
- MQ；
- 延迟查单；
- 分钟级补单；
- 通知重试；
- 配置缓存刷新；
- Redis token。

## 14.2 当前不足

- 未发现统一分布式任务锁；
- 未实现 Outbox；
- 未发现完整熔断和限流；
- MQ 多业务共用线程池；
- 通知和查单线程未隔离；
- 定时扫描使用页码分页，结果集缩小时可能跳过记录；
- 支付、退款、通知和分账的部分业务索引不足；
- 多实例任务可能重复扫描；
- 没有完整账务、对账和结算监控；
- 核心资金场景自动化测试不足。

## 14.3 分布式锁适用场景

- 定时任务选主；
- 日终对账；
- 结算批次生成；
- 出款执行；
- 热点账户冻结。

分布式锁不能替代：

- 订单唯一约束；
- 状态 CAS；
- 账务事件唯一；
- 结算明细唯一占用。

## 14.4 当前线程池

MQ 执行器配置：

```text
核心线程20
最大线程300
队列10
CallerRunsPolicy
```

商户通知和其他 MQ 任务可能共用。通知 HTTP 超时20秒，慢通知可能阻塞其他业务。

生产应隔离：

- 通知；
- 支付查单；
- 退款查单；
- 分账；
- 配置刷新。

## 14.5 异常阈值

建议分级：

```text
软超时：开始查询
异常阈值：告警
人工阈值：升级处理
业务失效：进入关闭/差错
```

参考：

- 支付：5秒查单、10分钟异常、30分钟人工、2小时业务过期；
- 退款：10分钟告警、30分钟检查、2小时升级；
- 转账：5分钟告警、30分钟人工、1天后独立处理；
- 分账：5分钟查询、30分钟告警、2小时人工。

阈值应结合实际渠道 P99、退款 SLA、金额和风险等级配置。

# 十七、面试可复用的简练表述

## 17.1 状态机

> 支付、退款和转账都以稳定平台订单号为核心，通过唯一业务键防重复创建，通过带旧状态条件的数据库 CAS 推进状态。渠道确认后的状态与通知、分账和账务通过唯一事件幂等衔接，重复回调和 MQ 重投不会重复产生资金结果。

## 17.2 并发退款

> 并发退款不能先查后调渠道。支付单加锁后校验成功退款、在途预占和本次金额，在同一短事务中创建退款单并预占额度，提交后才调用渠道。成功转已退款，失败释放，未知保持冻结并查原单。

## 17.3 最终一致性

> 通过事务性 Outbox 将业务状态变化和待发事件同事务落库，由中继可靠投递到 MQ；延迟消息处理通知和查单重试，定时任务兜底长期未决订单，无法自动收敛的异常升级人工处理。

## 17.4 对账

> 对账按账期下载渠道完整明细，先区分支付、退款、冲正和手续费，再分别与对应业务表匹配。支付匹配支付单，退款逐笔匹配退款单，之后汇总校验支付单累计退款。净额只能用于结算层校验，不能替代交易明细对账。

## 17.5 分账与结算

> 分账解决交易收入归谁，结算解决可结算资金何时出款。分账父任务结束不代表每个接收方成功，结算必须基于逐笔成功、已对账且未被冻结的账务事实。

# 二十、最终记忆卡

1. 渠道订单创建不等于用户支付成功。
2. 支付成功不等于通知成功、记账成功、结算成功。
3. 超时不是失败，未知必须查原渠道。
4. 支付、退款、转账必须有稳定业务幂等键。
5. 回调使用旧状态条件更新。
6. 重复回调不能重复通知、分账和记账。
7. 退款成功才更新支付单累计退款金额。
8. 并发退款必须在调用渠道前预占额度。
9. 转账超时不能换单号重发。
10. 分账不等于结算。
11. 父分账任务结束不等于每个接收方成功。
12. 对账按日期拉完整账单，交易类型分别匹配。
13. 退款逐笔匹配后再汇总支付单。
14. 平台有渠道无不能直接补单。
15. Outbox 解决状态与消息双写空档。
16. 长期未决靠定时查询和人工升级兜底。
17. 账务错误只能冲正，不修改历史分录。
18. 结算前退款扣待结算款，结算后退款扣余额或形成欠款。
19. 出款成功后退票仍需冲回。
20. Jeepay 是支付交易底座，不是完整支付结算公司系统。
